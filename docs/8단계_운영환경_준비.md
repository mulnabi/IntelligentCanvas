## 8-A 환경 분리

- `VITE_FIREBASE_MODE`는 `emulator` 또는 `production`이다. 기존 개발 서버의 `VITE_USE_FIREBASE_EMULATORS=true`는 계속 지원한다. 두 설정을 함께 쓴다면 같은 모드를 가리켜야 한다.
- 개발 모드는 루프백 오리진 및 기존 Emulator 프로젝트만 사용한다. Auth 9099·Firestore 8080·Functions 5001·Storage 9199의 연결 주소와 로컬 버킷은 코드에 고정한다. 개발 앱은 운영용 URL이나 버킷 환경 값을 사용하지 않는다.
- 운영 모드는 승인된 운영 빌드의 명시적 활성화 값, 고정 HTTPS 오리진과 실제 Web App 설정을 요구한다. 이 조건을 통과한 경우 SDK 네 종이 동일 앱을 쓰고 Emulator 연결 호출을 생략한다. 기본 빌드의 운영 연결은 닫혀 있다.
- 추가한 `firebaseEnvironment.js`는 SDK 초기화 전에 설정을 검증한다. `firebase.js`는 기존 Auth 저장과 미저장 그림 보호를 재사용한다. `firebaseServices.js`는 callable과 바이너리 API가 동일 환경·프로젝트·리전을 사용하게 한다. 개발용 `firebaseServerEmulators.js`는 검증 함수 전용이다. `.env.example`은 공개 입력 이름만 제공한다.

| 설정 | 로컬 개발 | 승인 이후 운영 빌드 |
| --- | --- | --- |
| `VITE_FIREBASE_MODE` | `emulator` 또는 기존 플래그만 사용 | `production`을 명시 |
| `VITE_USE_FIREBASE_EMULATORS` | 함께 설정할 때 `true` | 기존 `.env.local`에서 상속된다면 `false`로 덮어씀 |
| `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID`, `VITE_FIREBASE_MESSAGING_SENDER_ID` | 기존 Web App 값 사용. 기존 로컬 프로젝트 ID 유지 | Firebase 프로젝트 설정의 같은 Web App에서 모두 복사 |
| `VITE_FIREBASE_STORAGE_BUCKET` | 코드에 정의된 `intelligentcanvas-stage5a-local.invalid` 사용 | Console에서 확인한 기본 버킷 이름 입력 |
| `VITE_FIREBASE_FUNCTIONS_REGION`, `VITE_FIREBASE_FUNCTIONS_BASE_URL` | 고정 루프백 URL과 `asia-northeast3` 사용 | 승인·배포 후 실제 API 리전 및 Cloud Functions 기본 URL 확인. URL 끝에 슬래시를 붙이지 않음 |
| `VITE_FIREBASE_APP_ORIGIN`, `VITE_FIREBASE_ENABLE_PRODUCTION` | 운영 승인 값 없이 실행 | 프론트엔드 HTTPS 오리진만 입력. 서비스와 보안 확인을 마친 뒤에만 `true` |

- 현재 검증기는 Firebase 기본 인증 도메인, 기본 버킷 이름, 정규 Cloud Functions URL 형식을 지원한다. 별도 사용자 지정 도메인이나 버킷이 필요하면 허용 조건을 확장해야 한다. 오프라인 검사로는 API 키가 해당 프로젝트에 속하는지, 버킷이 실제로 존재하는지 확인할 수 없다. 실제 Web App 값은 Console에서 함께 대조한다.
- Vite의 `VITE_*`는 빌드 결과를 통해 읽을 수 있다. Firebase Web API 키는 프로젝트를 식별하는 공개 클라이언트 구성이다. 접근 권한은 Auth, Security Rules, 서버 검증으로 관리한다. Admin 인증 정보와 서비스 계정 키는 서버 런타임에서만 사용하며 `VITE_*`와 Git에 넣지 않는다. `.env.local`과 `.env.production.local`이 Git에서 제외되는 것을 확인했다. [Firebase API 키](https://firebase.google.com/docs/projects/api-keys) · [Firebase Admin SDK](https://firebase.google.com/docs/admin/setup)
- 오리진을 분리하면 Auth 브라우저 영속 정보와 `IntelligentCanvasLocal`도 브라우저에서 격리된다. 개발 오리진의 IndexedDB 작품과 Emulator 계정은 운영으로 자동 이전되지 않는다. Dexie v5의 작품·레이어·PNG·동기화 대기열·복구 초안 스키마는 기존 방식으로 사용한다.
- 환경 검사 7/7 통과. 기본 빌드를 Edge에서 열어 설정 오류와 비활성 로그인 버튼을 확인했다. 앱의 Firebase 네트워크 요청과 개발용 연결 검사 진입점은 관찰되지 않았다. 운영 설정의 정상 분기는 가짜 값의 파싱만 테스트했다.

## 8-B Storage·Functions·Firestore 운영 준비

### Cloud Storage

| 항목 | 현재 동작과 운영 전 필요한 일 |
| --- | --- |
| 버킷 | `firebase.json`과 서버 `bucket()`은 동일한 Emulator 버킷을 사용한다. 운영 동기화 검증을 승인받은 뒤 실제 기본 버킷을 확인하거나 활성화하고, 서버와 웹 빌드에 같은 버킷을 설정한다. 현재 실제 버킷 활성화 여부는 미검증이다. |
| 객체 경로 | 확정본은 `users/{uid}/artworks/{artworkId}/layers/{layerId}/{contentRevisionId}/raster.png`를 유지한다. 임시 파일은 같은 작품 아래 `staging/{requestId}/{layerId}/{uuid}/raster.png`에 저장한다. |
| 파일 검증 | 레이어당 8 MiB. PNG MIME, 서명·청크와 이미지 치수·크기·해시를 검증한다. 브라우저는 바이너리 요청을 사용하며 서버가 Firebase ID 토큰을 검증한 후 Storage를 사용한다. 크기 초과 시 브라우저 원본과 대기열을 보존한다. |
| 확정 원본 | 세션·버전·영수증 확인 후 새 콘텐츠 경로에 쓰고, 생성 전제조건과 확인된 바이트로 덮어쓰기를 방지한다. Firestore 트랜잭션이 새 참조를 확정한다. 작품 소프트 삭제 시에도 원본을 유지한다. Storage와 Firestore는 별도 서비스이므로 실패한 저장에 미확정 객체가 남을 수 있다. |
| 임시 파일 | 24시간이 지난 종료 요청만 분리된 staging 경로에서 확인한다. 기본은 시뮬레이션이며 실행 시 객체 세대 조건을 검사한다. 진행 중 요청과 확정 원본 경로를 정리하지 않는다. 운영에서는 일반 사용자에게 정리 함수 권한을 노출하지 않는 별도 운영 절차가 필요하다. Firestore 참조를 검사하는 범위를 검토하기 전에 광범위한 객체 수명 정책을 적용하지 않는다. |
| 규칙·IAM | `storage.production.rules`는 브라우저의 직접 객체 읽기·쓰기를 모두 거부한다. 운영 Functions 서비스 계정에 승인된 버킷 범위의 최소 권한을 부여하고, 객체 공개 정책과 IAM도 따로 확인한다. 로컬 Storage Emulator로 실제 IAM을 검증할 수 없다. |
| 리전·비용 | 사용자 위치·데이터 요구사항·분산 비용을 기준으로 Firestore와 Storage 및 Functions 리전을 함께 결정한다. 현재 로컬 설정의 `asia-northeast3`을 운영 리전으로 자동 적용하지 않는다. PNG 저장량, 객체 작업, 다운로드 전송, 리전 간 전송 정책을 확인한다. |

Cloud Storage for Firebase를 사용하려면 Blaze가 필요하다. 현재 1~7단계 로컬 개발에는 실제 버킷이 필요하지 않다. [Cloud Storage 시작하기](https://firebase.google.com/docs/storage/web/start) · [Storage 가격](https://cloud.google.com/storage/pricing) · [Storage IAM 역할](https://cloud.google.com/storage/docs/access-control/iam-roles) · [Storage Emulator의 차이](https://firebase.google.com/docs/emulator-suite/connect_storage#differences_from_production)

### Cloud Functions

- `functions/`은 CommonJS, Functions 2세대, Node.js 22다. `firebase-functions` 7.4.0과 `firebase-admin` 14.5.1을 사용한다. Firebase CLI 설정과 패키지의 Node.js 설정을 대조했다. 배포를 검토할 때 Node.js 22로 의존성을 설치하고 통합 검사를 다시 실행한다. [함수 런타임 관리](https://firebase.google.com/docs/functions/manage-functions#set_nodejs_version)
- 현재 서버 Admin 앱은 명시적인 Emulator 신호와 루프백 설정을 요구한다. `functions/src/index.js`에서도 같은 실행 구분으로 함수 등록을 제한했다. Emulator 신호가 없는 일반 함수 검색에서 등록되는 함수가 0개임을 검사했다. 이 패키지로 운영 API를 서비스할 수 있는 상태는 아니다.
- 운영 검토 때 별도의 운영 진입점과 Admin 초기화 경로를 마련한다. 승인된 프로젝트·버킷·리전, 관리형 서비스 계정과 ADC, 운영 웹 오리진 CORS를 지정한다. 인증·세션·업로드·삭제에 사용하는 실제 업무 함수만 명시적으로 등록한다. `checkServerEnvironment`, 테스트 규칙, staging 정리용 사용자 호출은 운영 진입점에서 제외한다. 프로덕션 ID 토큰 검증과 서비스 계정 권한은 승인된 환경에서 따로 검사한다. [Admin SDK](https://firebase.google.com/docs/admin/setup) · [Functions 리전](https://firebase.google.com/docs/functions/locations) · [HTTP 함수와 CORS](https://firebase.google.com/docs/functions/http-events)
- 기존 callable의 인증 UID, 작품 소유권, 세션 자격, `generation`, `serverVersion` 검증과 영수증의 `requestId` 멱등성을 유지한다. 바이너리 응답은 토큰을 노출하지 않고 실패 종류별 HTTP 코드와 메시지를 반환한다. 운영 로깅에는 요청 ID·단계·오류 코드만 기록하고 토큰·세션 proof·PNG 요청 본문은 제외한다. 운영 전 오류율, 제한 시간, 메모리, 최대 인스턴스와 전송량을 정한다.

### Firestore 규칙과 복합 인덱스

- `users/{uid}`의 프로필에는 소유자 읽기와 제한된 생성·수정만 허용한다. `users/{uid}/artworks/{artworkId}` 및 `layers`는 소유자 읽기만 허용한다. `serverVersion`, 소프트 삭제 상태, 레이어 원본 참조, 편집 세션, `revisions`, `saveReceipts`는 함수가 관리한다. 내부 하위 컬렉션의 직접 접근은 기본 거부 규칙을 따른다.
- `firestore.production.rules`는 기존 핵심 권한을 유지하면서 `connectionTests` 경로를 제거한다. 현재 `firebase.json`에는 기존 Emulator 규칙이 연결되어 있으므로, 승인 전에는 운영 대상 구성으로 이 파일을 사용하지 않는다. 두 운영 후보 규칙은 정적 검사를 수행했다. Firebase 운영 규칙 게시 및 권한 검사는 미검증이다.
- `firestore.indexes.json`의 세 복합 인덱스는 현재 서버 목록 쿼리와 일치한다. 범위는 `COLLECTION`의 `artworks`이며 공통 등호 필드는 `ownerUid`, `publication`, `state`다. 마지막 정렬은 각각 `updatedAt DESC`, `createdAt DESC`, `title ASC`다. 커서가 쓰는 문서 ID의 방향은 각 인덱스 기본 `__name__` 방향과 같다. 현재 페이지 쿼리에서 추가로 필요한 복합 인덱스는 발견되지 않았다. 실제 프로젝트에서는 해당 인덱스 3개를 설정하고 사용 가능한 상태가 될 때까지 기다린 뒤, 기본 정렬·생성일·제목과 동률 페이지를 검증한다. [Firestore 인덱스 개요](https://firebase.google.com/docs/firestore/query-data/index-overview) · [인덱스 관리](https://firebase.google.com/docs/firestore/query-data/indexing)

이번 작업에서 React 화면과 CSS는 수정하지 않았다. 계획서에 있던 객체 JSON·AI 제안·별도 획 단위 복구 기록은 현재 릴리스 검증 범위에 포함되지 않는다. 6~7단계에서 정한 PNG 중심 저장과 소프트 삭제 보존 정책을 그대로 확인했다.

### 로컬에서 직접 확인

1. Emulator가 이미 실행 중이면 재사용한다. 별도 실행할 경우 기존 프로젝트에서 `firebase.cmd emulators:start --only auth,firestore,storage,functions --project ai-drawing-a9177`을 실행한다.
2. 터미널을 하나 더 열고 `npm.cmd run dev -- --host 127.0.0.1`을 실행한다. 기존 `.env.local`로 브라우저에서 터미널이 표시한 루프백 주소를 연다. 같은 주소와 포트를 유지해야 이전 로컬 작품을 계속 볼 수 있다.
3. 서로 분리된 프로필 A와 B에서 같은 Emulator 계정으로 로그인한다. A에서 새 테스트 작품을 만들고 저장한 뒤 서버에 등록한다. 레이어 PNG를 서버에 저장하고 B의 목록에서 열어 픽셀과 읽기 전용 상태를 확인한다.
4. 테스트 작품에서 A를 오프라인으로 전환하고 그린 뒤 B에서 강제 복구로 변경을 확정한다. A를 다시 연결해 서버 작품 보기에서 B의 확정본을 열고 A의 복구 초안과 구분되는지 확인한다.
5. `node --test scripts/test-firebase-environment.mjs`로 환경 설정 검사를 실행한다. 브라우저 통합 검사 파일은 `scripts/test-auth-recovery.mjs`, `scripts/test-server-emulators.mjs`, `scripts/test-artwork-metadata.mjs`, `scripts/test-canvas-persistence.mjs`, `scripts/test-edit-sessions.mjs`, `scripts/test-artwork-sync.mjs`, `scripts/test-offline-recovery.mjs`다.
