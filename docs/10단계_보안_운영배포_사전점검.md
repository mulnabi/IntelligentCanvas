작업 시작 때 로컬 `database`와 `origin/database`가 같은 커밋을 가리켰고 작업 트리는 깨끗했다. 실행 중인 Firebase Emulator를 재사용했다. 실제 운영 대상과 자격 증명을 입력하거나 Firebase 서비스를 활성화하지 않았다. 기존 DB, 규칙, 사용자 데이터와 Git 이력은 보존했다.

## 10-A npm 감사와 패치

`npm.cmd audit --json`과 `npm.cmd --prefix functions audit --json`을 공식 npm 레지스트리에서 각각 패치 전후에 실행했다.

| 트리 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 프론트엔드 전체 설치 트리 | high 6개 | high 4개 |
| Functions | 0개 | 0개 |

감사 결과의 개수는 영향받는 패키지 항목 수다. 직접 의존성 `firebase`와 Firestore·compat·gRPC로 이어지는 네 항목의 근본 원인은 설치 트리의 같은 gRPC 의존성이다.

| 직접·간접 및 버전 | 조치 및 영향 |
| --- | --- |
| 직접 개발 의존성 `vite` 8.3.1 → **8.3.3** | Vite 8.3 계열의 공식 보안 패치로 고정했다. 감사에서 지적한 Windows 편집기 연동과 개발 서버 항목이 해결됐다. 배포용 정적 JS는 개발 서버를 실행하지 않는다. 잔여 gRPC 공지의 영향 대상은 Node gRPC 서버의 인증 컨텍스트 및 오류 메시지 처리다. Vite 8.3.3의 빌드 모듈 목록에 Firestore 웹 모듈이 있었으며 `@grpc/grpc-js`, `firebase-admin`, `source-map-js`는 포함되지 않았다. Cloud Functions 트리는 Admin SDK 경로에서 gRPC 1.14.7을 사용한다. 프론트엔드 의존성을 쓰는 Node 도구나 향후 SSR을 추가할 때 잔여 항목의 실행 경로를 다시 평가한다. Functions 의존성과 잠금 파일은 그대로 사용했다.

## 10-B 운영 진입점과 보안 점검

`functions/src/production.js`를 별도 진입점으로 추가했다. 패키지의 기존 진입점은 `INTELLIGENTCANVAS_FUNCTIONS_MODE=production`일 때만 이를 선택한다. 기본 상태에서 운영 함수는 등록되지 않으며, 로컬 함수들은 기존 Emulator 환경에서 계속 실행된다.

- 운영 설정은 프로젝트 ID, 동일 프로젝트의 실제 기본 Storage 버킷, Functions 리전, 정확한 웹 HTTPS 오리진, 같은 프로젝트의 전용 서비스 계정 이메일을 모두 요구한다. 배포 탐색과 실행 환경에서 감지한 프로젝트가 다르거나 Emulator 및 SDK 디버그 변수가 섞이면 차단한다.
- 운영 요청은 관리형 Functions 런타임과 일치하는 `FIREBASE_CONFIG`를 요구한다. 서비스 계정 키 파일을 지정한 실행은 차단한다. Callable SDK와 PNG HTTP 핸들러는 같은 기본 Admin 앱의 ID 토큰 대상 프로젝트를 사용한다. 실제 프로젝트의 IAM 권한은 승인 후 확인한다. [Admin SDK 초기화](https://firebase.google.com/docs/admin/setup) · [Functions 환경 설정](https://firebase.google.com/docs/functions/config-env)
- 운영에서 업무 API 15개를 명시적으로 등록한다. `checkServerEnvironment`와 `cleanupArtworkStaging`는 등록 목록에서 제외했다. 향후 staging 정리에는 별도 관리 주체, 접근 권한과 보존 기준이 필요하다.
- HTTPS 트리거는 Firebase 웹 SDK가 호출할 수 있도록 인보커를 설정한다. 사용자 데이터 접근은 Firebase ID 토큰과 업무 권한으로 검사한다. CORS 응답은 승인한 하나의 웹 오리진에만 허용하며, 그 외 `Origin`을 가진 요청은 핸들러에서도 거부한다. `Origin`이 없는 클라이언트 요청에도 Firebase 인증이 필요하다. [Functions HTTP 및 CORS](https://firebase.google.com/docs/functions/http-events)
- 8 MiB PNG의 압축 해제 메모리를 고려해 업로드·다운로드·확정 함수에 인스턴스당 동시 처리 1건, 512 MiB 설정을 적용했다. 예상 부하와 최대 인스턴스 한도는 운영 전 확인한다.

| 점검 | 결과 |
| --- | --- |
| Firebase UID와 작품 소유권 | Callable의 검증된 `request.auth.uid`와 바이너리 요청의 검증된 Firebase ID 토큰 UID를 사용한다. 컬렉션 및 객체 경로는 서버가 UID로 계산한다. 조회·저장·삭제 시 문서의 `ownerUid`를 대조한다. |

## 10-C 사용자 설정 체크리스트

실제 환경은 별도 승인을 받은 후 다음 순서로 준비한다.

1. **대상 프로젝트와 요금제**. 실제 Firebase 프로젝트 ID와 배포 권한을 확인한다. Functions 배포와 실제 Cloud Storage for Firebase 사용에는 Blaze가 필요하다. 로컬 Emulator 검증과 현재 코드 준비는 실제 버킷 활성화 없이 진행할 수 있다. **실제 Storage가 필요한 시점은 승인된 클라우드에서 최초로 PNG 업로드·다운로드를 검증하기 직전**이다. [Functions 시작하기](https://firebase.google.com/docs/functions/get-started) · [Cloud Storage 시작하기](https://firebase.google.com/docs/storage/web/start)
2. **Storage 및 Firestore 지역**. Firestore `(default)` DB와 실제 기본 버킷의 위치를 확인한다. 앱 사용자, 데이터 위치, 버킷→Functions 전송 비용을 고려해 Functions 리전을 선택한다. 실제 기본 버킷 이름을 Functions와 웹 빌드에 동일하게 지정한다.
3. **Auth·웹 앱**. 실제 Web App 설정과 Auth의 사용할 로그인 공급자·Authorized Domains를 확인한다. 승인된 HTTPS 배포 오리진이 브라우저 설정 및 서버 CORS와 일치해야 한다. 개발 계정·UID 및 IndexedDB 데이터의 운영 이전 여부는 별도 결정한다. [Firebase 이메일 인증](https://firebase.google.com/docs/auth/web/password-auth)
4. **Functions 실행 계정과 환경**. 전용 관리형 서비스 계정 이메일과 최소 권한을 마련한다. `functions/.env.example`의 변수는 실제 값으로 채운 운영 프로젝트 전용 파일 또는 배포 환경에 넣고 Git에서 제외한다. Firebase가 제공하는 `FIREBASE_CONFIG`와 `K_SERVICE`는 직접 설정하지 않는다. 서버 비밀이 필요한 후속 기능은 Secret Manager를 검토한다. 서비스 계정 키를 브라우저 `VITE_*` 변수에 넣지 않는다. Node.js 22에서 릴리스를 검증한다. [Functions 런타임](https://firebase.google.com/docs/functions/manage-functions#set_nodejs_version) · [보안 환경 변수](https://firebase.google.com/docs/functions/config-env)
5. **운영 구성과 규칙**. 별도 승인 후 `firebase.production.example.json`의 구조로 대상 프로젝트 전용 구성을 마련한다. 예시의 Storage 규칙은 승인된 기본 버킷을 대상으로 검토한다. 운영 후보 `firestore.production.rules`, `storage.production.rules`와 복합 인덱스 3개를 사용한다. 세 쿼리는 `ownerUid`, `publication`, `state`를 공통으로 쓰고 `updatedAt DESC`, `createdAt DESC`, `title ASC`로 정렬한다. 인덱스 준비 후 페이지 요청과 타 UID·미로그인 접근 거부를 재검증한다. [Firestore 인덱스 관리](https://firebase.google.com/docs/firestore/query-data/indexing)
6. **웹 환경변수**. [8단계 문서](./8단계_운영환경_준비.md#8-a-환경-분리)의 `VITE_FIREBASE_` 설정을 승인한 실제 값으로 준비한다. Functions 리전·기본 URL과 운영 오리진을 확인한 뒤 양쪽 보호 검증에 통과했을 때만 웹 연결을 활성화한다.
7. **보존·비용·모니터링**. Firestore 백업 주기·보존·복구 시험과 Storage 확정 PNG 보존 정책을 정한다. 복원 후 Firestore 참조와 실제 객체가 일치해야 한다. IndexedDB의 로컬 전용 초안은 클라우드 백업에 포함되지 않는다. Firestore 문서·인덱스 작업과 백업, Storage 용량·객체 작업·전송, Functions 실행·동시성·빌드와 로그 보존을 측정한다. 비용 알림과 사용 한도 대응 절차를 함께 준비한다. 예산 알림은 사용량을 자동 중단하지 않는다. [Firestore 백업](https://firebase.google.com/docs/firestore/backups) · [Firebase 가격](https://firebase.google.com/pricing) · [Cloud Billing 예산](https://cloud.google.com/billing/docs/how-to/budgets)

**기존 135개와 신규 4개, 최종 139/139 통과.** 독립 Edge 프로필을 쓴 브라우저 테스트는 로컬 Emulator 대상이다. 기본 빌드 미리보기에서 운영 설정이 잠긴 상태와 Firebase 요청 0건도 확인했다. 처음 CORS 검사는 SDK가 원소 하나의 배열을 고정 응답 헤더로 변환하는 동작을 발견했다. 승인 오리진과 정확히 일치하는 정규식으로 바꾸고, 허용 오리진 preflight 및 비허용 오리진의 헤더·응답을 다시 확인했다.

**Node.js 호환성.** Node.js 24.20.0으로 Edge·Emulator 회귀를 실행했다. 별도로 공식 배포 파일의 SHA-256을 대조한 Node.js 22.23.5에서 환경 검사 11/11, Vite 빌드, Admin SDK 14.5.1 및 Functions SDK 7.4.0 로딩이 통과했다. 같은 런타임에서 Functions SDK 탐색으로 2세대 업무 API 15개가 있는 manifest를 생성했다. 운영 모드의 거부·CORS 검사는 가짜 설정과 루프백 요청만 사용했다.

**구현했지만 운영 미검증.** 실제 Cloud Functions 배포·실행, 관리형 계정 권한, 운영 Auth 토큰과 리전·오리진, 실제 버킷 접근, 운영 Rules 적용과 인덱스 활성화, Cloud Logging과 비용, 실제 휴대폰·펜은 확인하지 않았다. 운영 연결 전에 승인된 테스트 환경에서 권한·업로드·복원과 부하를 확인한다. 기존 DB, 로컬 보존 데이터와 활성 Emulator 데이터는 초기화하지 않았다. Git 커밋·푸시와 운영 Firebase 변경은 수행하지 않았다.

### 직접 확인과 실제 기기 계획

1. 로컬에서는 기존 Emulator를 켜고 Playwright가 설치된 환경에서 `node scripts/test-auth-recovery.mjs`, `test-artwork-metadata.mjs`, `test-canvas-persistence.mjs`, `test-server-emulators.mjs`, `test-edit-sessions.mjs`, `test-artwork-sync.mjs`, `test-offline-recovery.mjs`를 실행한다. 각 파일의 경로는 `scripts/`다. 첫 단계 Auth·Firestore 연결 검사는 개발 브라우저의 `window.runFirebaseSmokeTest()`로 확인한다.
2. 로컬에서 `node --test scripts/test-firebase-environment.mjs scripts/test-functions-production.mjs`로 보호 설정을 확인한다. 운영 진입점 검사는 가짜 설정과 로컬 HTTP 요청만 사용한다.
