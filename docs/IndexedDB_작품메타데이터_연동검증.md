# 2단계: IndexedDB 작품 메타데이터와 작품 목록 연동

구현·검증일: 2026-11-19

> 2026-11-20 후속 구현: [3단계 Canvas PNG 저장·복원](./Canvas_PNG_저장복원_연동검증.md)에서 기존 데이터를 보존하며 Dexie v2와 `canvasContents`를 추가했다. 실제 Canvas 해상도 및 PNG 저장·복원이 연결됐고, 갱신한 기존 통합 검사 24개가 다시 통과했다. 아래 v1·800×800·그림 미저장 설명은 2단계 당시 기록이다.

설계 기준: [최신 DB 구축 계획서](./IntelligentCanvas_DB_구축계획_개정본_2026-11-16.md)의 3장, 5장, 7장, 11장, 12장. 기존 [Auth·프로필 연동](./Auth_프로필_연동검증.md)을 재사용한다.

이번 단계는 **로그인한 UID의 작품 메타데이터를 현재 브라우저에 저장하고, 기존 목록과 그림판 진입 경로에 연결**한다. 실제 그림 픽셀, 레이어 저장, 서버 작품 동기화와 편집 세션은 구현하지 않았다.

## DB·테이블·필드

기존 소스에 Dexie DB 초기화가 없는 것을 확인해 다음 DB 하나를 만들었다.

- DB 이름: `IntelligentCanvasLocal`
- Dexie 버전: `1`
- 테이블: `artworks` 하나
- 기본키: `[uid+artworkId]`
- 인덱스: `[uid+state+updatedAt]`, `[uid+state+createdAt]`

```javascript
localDb.version(1).stores({
  artworks: '[uid+artworkId], [uid+state+updatedAt], [uid+state+createdAt]',
})
```

| 필드 | 내용 |
|---|---|
| `artworkId` | `crypto.randomUUID()`로 생성하는 UUID v4 |
| `uid` | 현재 로그인한 Firebase UID |
| `title` | 앞뒤 공백 제거한 제목, 최대 200자. 새 작품의 빈 제목은 `제목 없음` |
| `titleNormalized` | NFKC 정규화·앞뒤 공백 제거·소문자 변환한 검색용 값 |
| `width`, `height` | 가로·세로 픽셀 수. 1~8192 정수, 기본 800×800 |
| `backgroundColor` | `#rrggbb` 형태. 현재 입력 UI가 없어 기본 `#ffffff` |
| `createdAt` | 로컬 `Date.now()` 밀리초 숫자, 최초 생성 후 유지 |
| `updatedAt` | 생성·제목 수정·삭제 시 로컬 `Date.now()` 밀리초 숫자 |
| `schemaVersion` | 메타데이터 구조 버전 `1` |
| `state` | `active` 또는 `deleted` |
| `deletedAt` | 활성 작품은 `null`, 삭제하면 로컬 밀리초 숫자 |

이 시각은 사용자 기기의 시계 기준이며 **Firestore 서버 Timestamp가 아니다.** 기기의 시계가 바뀌면 날짜 정렬에도 영향을 줄 수 있다. Dexie DB 버전과 각 레코드의 `schemaVersion`도 별개다.

기본키가 UID와 작품 ID를 함께 사용하므로 모든 단건 작업에 소유자가 포함된다. 목록은 현재 UID의 `active` 상태만 해당 날짜 인덱스로 조회한 후 제목 부분 검색을 적용한다. 생성일·수정일은 최신순, 기존 이름순은 한국어 문자열 비교를 사용한다. 동일한 정렬값은 작품 ID로 보조 정렬한다.

## 사용자 구분과 계정 변경

1. 화면은 기존 `useAuth()`가 제공하는 Firebase UID를 사용한다.
2. Repository는 전달받은 UID를 그대로 신뢰하지 않고 실제 `auth.currentUser.uid`와 비교한다.
3. 조회·쓰기 전후에 UID를 재검사한다. 쓰기 트랜잭션 도중 계정이 바뀌면 취소한다.
4. 개별 작품 조회·수정·삭제는 `[현재 UID, artworkId]` 키만 사용한다.
5. 다른 사람의 ID, 없는 ID, 삭제한 ID는 모두 열 수 없다는 같은 안내를 표시한다.
6. 계정 변경 시 목록·관리 팝업·그림판을 새 계정 기준으로 다시 구성한다. 이전 비동기 조회 결과도 숨긴다.
7. 로그아웃은 로컬 작품 데이터를 삭제하지 않는다. 같은 UID로 다시 로그인하면 다시 보인다.

**이는 앱 수준의 데이터 구분이다.** 같은 브라우저 프로필을 직접 사용하는 사람이나 개발자 도구는 IndexedDB를 열 수 있다. 암호화 저장소나 Firestore Security Rules 같은 서버 보안 경계가 아니다.

## 목록과 그림판 흐름

- 새 작품 저장 성공 → 팝업 닫기 → 검색어 초기화·최근 수정순으로 새 작품 표시.
- 카드 클릭/Enter → `/drawing/{artworkId}` 이동.
- `ArtworkDrawingPage`가 현재 UID의 작품을 조회 → `DrawingSpace`에 `artwork` 객체 전달.
- 제목 변경·삭제 시 Dexie `liveQuery` 구독으로 목록 자동 갱신. 같은 사이트의 다른 탭에서 일어난 메타데이터 변경도 반영한다.
- 다른 탭에서 열린 작품이 삭제되면 해당 그림판도 닫고 안내한다. 이것은 삭제 상태 반영이며 편집 세션 잠금은 아니다.
- 기존 ID 없는 `/drawing`은 작품 목록 `/`으로 이동한다. 임의 작품을 자동 생성하지 않는다.
- 비로그인 목록·그림판은 로그인 안내를 표시하고 Repository 작업을 차단한다.

카드의 기존 썸네일 영역은 `미리보기 없음`을 사용한다. 저장한 레이어 수가 없으므로 더미 레이어 수 대신 실제 수정일과 작품 크기를 표시한다. 기존 카드·팝업의 CSS와 배치는 유지했다.

그림판 하단 안내에는 작품 제목·저장한 크기·목록 링크와 **그림은 저장되지 않음**을 표시한다. 저장한 크기가 800×800과 다르면 현재 Canvas가 여전히 800×800이라는 안내도 표시한다.

## 계획서와 실제 코드에 맞춘 선택

| 차이/미정 항목 | 이번 단계 처리 |
|---|---|
| 계획서의 Firestore 필드가 `ownerUid`, `widthPx`, `heightPx` | 이번 요청의 로컬 계약인 `uid`, `width`, `height` 사용. 서버 연동 단계에서 변환하며 중복 필드는 만들지 않음 |
| 계획서의 Dexie 구조는 레이어·콘텐츠·대기열 등 전체 설계 | `artworks`만 구현. 추후 실제 저장 계약에 맞춰 테이블 추가 |
| 크기 기본값·상한이 생성 UI와 문서에 없음 | 실제 Canvas/CSS를 근거로 800×800·흰색 사용. 8192px 상한과 제목 200자 제한은 초기 입력 검증 정책이며 Canvas 지원 크기 보장이 아님 |
| 생성 메뉴 프리셋에 크기와 무관한 정렬 선택지가 있음 | 크기 프리셋을 임의 구현하지 않고 기존 위치에 비활성 `직접 입력` 표시 |
| 계획서의 삭제는 서버까지 확정하는 삭제 표식 | 로컬에만 `state=deleted`, `deletedAt` 저장. 서버 삭제 확정·파일 정리·휴지통 복원 미구현 |
| 계획서 전체 단계 번호와 이번 요청의 1·2·3단계 번호 | 요청 범위대로 2단계는 메타데이터만. 3단계에서 픽셀·레이어 저장과 좌표 계약을 다룰 예정 |

DB를 삭제하거나 테이블 전체를 비우는 초기화 코드는 없다. 후속 스키마 변경은 현재 `version(1)`을 유지하고 새 버전과 필요한 `upgrade()`를 추가해야 한다. 미래 스키마로의 실제 마이그레이션은 아직 없으므로 이번에 검증했다고 주장하지 않는다.

## 자동 검증 결과

Windows Edge의 별도 브라우저 컨텍스트에서 실제 IndexedDB와 Auth·Firestore Emulator를 사용했다. 최종 **24개 통합 검증 항목이 통과**했다.

| 요청한 검증 | 결과 |
|---|---|
| 작품 생성·제목·크기·배경·UUID·로컬 시각 저장 | 통과 |
| 같은 UID 작품 목록 조회 | 통과 |
| 제목 부분 검색·대소문자/정규화 검색·검색 결과 없음 | 통과 |
| 생성일·수정일·이름순 정렬 | 통과 |
| 제목 변경·생성일 유지·수정일 갱신 | 통과 |
| 삭제·목록 제외·삭제 작품 열기 차단 | 통과 |
| 삭제 확인에서 취소하면 데이터 그대로 유지 | 통과 |
| 페이지 새로고침·DB 연결 재열기 후 데이터 유지 | 통과 |
| A의 A1/A2 → B의 B1만 표시 → A 재로그인 시 A1/A2 복원 | 통과 |
| B가 A의 작품 ID로 직접 열기·수정·삭제 또는 UID 위조 | 모두 차단 |
| 로그아웃 시 목록·팝업·열린 그림판 초기화, 로컬 기록 보존 | 통과 |
| 올바른 작품 ID 경로·메타데이터 전달 | 통과 |
| 기존 회원가입·동일 닉네임·프로필 저장·로그인·잘못된 비밀번호 | 통과 |
| 중복 제출, 잘못된 크기·공백 제목, 저장 실패 후 입력값 유지 | 통과 |
| 닫힌 DB 조회 오류·재연결 후 다시 시도 | 통과 |
| 다른 탭 메타데이터 변경·삭제 반영 | 통과 |
| Canvas 기본 드로잉·레이어 패널 표시·모바일 생성 메뉴 | 통과 |
| 외부 서버 요청·서버 작품 요청·처리되지 않은 브라우저 오류 | 없음 |

저장 실패는 테스트 브라우저의 Dexie 생성 훅에서 `QuotaExceededError`를 발생시켜 검사했다. 실제 디스크를 가득 채우지는 않았다. DB 연결 종료 시 Dexie `liveQuery`가 오류를 전달하지 않아 로딩이 계속되던 경우를 발견해, Repository에서 사용자에게 전달할 수 있는 오류로 변환했다.

테스트 브라우저는 사용자 브라우저와 분리되어 있다. 테스트가 생성한 Auth 계정과 프로필 2개만 로컬 Emulator 관리 API로 정리하며 기존 계정이나 기존 IndexedDB를 전체 삭제하지 않는다. 스크립트는 결과 JSON과 화면 이미지를 시스템 임시 폴더에 저장하고 경로를 출력한다.

`npm.cmd run build`: 성공. 번들 500 kB 초과 경고가 있으나 빌드 실패는 아니다.

`npm.cmd run lint`: 오류 0개, 기존 그림판 관련 경고 7개. PowerShell에서 `npm.ps1` 실행 정책 오류가 나면 보안 정책을 바꾸지 않고 `npm.cmd`를 사용하면 된다.

### 자동 검사 재실행

Auth·Firestore Emulator가 실행 중이고 Edge와 Playwright가 준비된 환경에서 실행한다. 스크립트가 Vite를 **5187 포트**에서 직접 시작하고 종료하므로 별도 React 실행은 필요 없다.

```powershell
node scripts/test-artwork-metadata.mjs
```

Playwright가 이 프로젝트의 의존성으로 설치되어 있지 않다면 위 명령만으로 실행되지 않는다. 이번 검증에서는 실행 환경에 이미 제공된 Playwright를 사용했으며 프로젝트 패키지·잠금 파일은 변경하지 않았다. 별도 설치된 Playwright를 사용할 때는 해당 모듈의 실제 `index.mjs` 경로를 `PLAYWRIGHT_MODULE_PATH` 환경변수로 지정한다. 기본 브라우저는 Edge이며 필요하면 `TEST_BROWSER_CHANNEL`을 설정한다.

## 미완성 범위와 주의 사항

- **그림은 저장되지 않는다.** 새로고침하면 Canvas 픽셀과 현재 레이어 조작 상태는 사라진다. 작품 제목·크기 등 메타데이터만 남는다.
- Canvas는 여전히 800×800이다. 3단계에서 저장 크기 적용, 좌표계, 픽셀·레이어 저장/복원 계약을 구현해야 한다.
- 초기 레이어 기록, PNG Blob, 객체 JSON, 썸네일 생성, 큐·복구 초안은 아직 없다.
- Firebase Storage, Firestore 작품 동기화, Functions, 편집 세션, generation, 서버 수정 이력은 없다. 다기기 동시 편집 안전성을 보장하지 않는다.
- 로컬 삭제 표식은 서버로 전송되지 않는다. 목록에서 삭제되지만 개발자 도구에서 원시 기록은 볼 수 있다. 휴지통 UI는 없다.
- 로그인 상태가 유지된 페이지에서 로컬 저장은 가능하지만, 앱 재실행을 위한 PWA 오프라인 캐시는 이번 범위가 아니다.
- 브라우저 데이터 삭제·기기 분실 시 로컬 작품을 복구할 서버 사본이 없다.
- IndexedDB는 같은 브라우저 프로필·같은 사이트 주소에 종속된다. `localhost`/`127.0.0.1`, 포트, 브라우저가 달라지면 다른 저장소다.
- Emulator 계정을 지웠다가 같은 이메일로 다시 만들면 UID가 달라질 수 있다. 이전 UID 작품은 자동으로 새 계정에 넘기지 않는다. 확인 중에는 Emulator의 기존 계정을 유지한다.

## 직접 확인: Emulator → React → 가입·로그인 → 생성 → 새로고침 → 목록

### 1. Emulator 실행

이미 켜져 있으면 그대로 사용한다. 꺼져 있을 때 프로젝트 루트의 터미널에서 실행한다.

```powershell
firebase.cmd emulators:start --only auth,firestore --project ai-drawing-a9177
```

UI: `http://127.0.0.1:4000`. 기존 `.env.local`과 1단계 Firebase 설정을 그대로 사용하며 설정값을 콘솔에 출력할 필요가 없다.

### 2. React 실행

다른 터미널에서 실행하고, 이후 같은 주소를 사용한다.

```powershell
npm.cmd run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

### 3. 회원가입·로그인

`http://127.0.0.1:5173/signup`에서 테스트용 이메일과 8자 이상의 비밀번호로 가입한다. 이미 있는 계정은 `/login`에서 로그인한다. 성공하면 기존 작품 목록 `/`으로 이동한다. 처음에는 더미 카드 없이 빈 목록이 보인다.

### 4. 작품 생성

**+ 새 작품** → 제목 `A1 풍경`, 가로 `1024`, 세로 `768` → **확인**. 목록에 새 카드가 나타난다. 같은 방법으로 `A2 연습`을 만든다.

카드에 저장한 크기가 표시되는지 확인한다. 카드 클릭 시 주소가 `/drawing/고유-ID`가 되고 하단에 제목·크기와 미저장 안내가 나타난다. **작품 목록** 링크로 돌아온다.

### 5. 새로고침

목록에서 F5를 누른다. 로그인 복구가 끝나면 두 작품이 다시 표시되어야 한다. 그림판에 그린 선이 사라지는 것은 이번 단계의 미구현 범위이며 메타데이터 저장 실패와 다르다.

### 6. 작품 목록 확인

- 검색창에 `풍경`을 입력하면 해당 작품만 표시된다.
- 정렬을 최근 생성순·최근 수정순으로 바꾼다.
- 카드의 **⋮** → 제목 수정 → **제목 변경**. 수정순에서는 해당 작품이 위로 올라온다.
- **⋮ → 삭제 → 취소**하면 작품이 남는다. 삭제를 승인하면 목록에서 사라진다.
- `F12 → Application → IndexedDB → IntelligentCanvasLocal → artworks`에서 원시 메타데이터를 확인한다. 필요하면 개발자 도구의 새로고침 버튼을 누른다. Firestore Emulator에 작품 문서가 없는 것이 정상이다.

사용자 구분까지 확인하려면 A1/A2를 유지한 상태에서 Console에 다음을 실행해 로그아웃한다.

```javascript
await (await import('/src/services/authService.js')).logoutUser();
```

다른 이메일로 B 계정을 가입하고 B1만 만든다. A1/A2가 보이지 않아야 한다. 복사해 둔 A1의 `/drawing/ID` 주소로 직접 접속해도 열리지 않아야 한다. 다시 로그아웃하고 A로 로그인하면 A1/A2만 보여야 한다. 별도 로그아웃 화면이나 버튼은 추가하지 않았다.
