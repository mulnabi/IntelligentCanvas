## 9-A 기준과 연결 구조

작업 시작 시 로컬 `database`와 `origin/database`는 `f0a9c0e`에서 일치했고 작업 트리는 깨끗했다. `git show`로 병합의 부모에 `5d22de0 feat:페이지 연결`이 포함된 것을 확인했다. 기존 로컬 Firebase Emulator 네 종과 UI를 재사용했다. 브라우저 검사는 서로 격리된 Edge 프로필과 실행마다 새로 만든 테스트 계정·작품을 사용했다.

| 화면·계층 | 실제 경로 및 데이터 연결 |
| --- | --- |
| 로그인·회원가입 | `App.jsx` 라우트 → `useAuth` → `authService`/`authSession` → Firebase Auth → `userService` → Firestore 프로필. Auth 복원에서 무효 토큰을 처리하고, 인증 전환 전에 현재 그림 저장을 기다린다. |
| 작품 목록 | `/` → `ArtworkList`, `ArtworkCard`, `ArtworkActions` → `useArtworks`, `artworkRepository`. `artworkSyncService`를 통해 서버 20개 단위 페이지와 삭제 표식을 불러온다. 같은 ID의 로컬·서버 카드는 하나로 표시한다. 검색 범위는 로컬 작품과 불러온 서버 페이지다. 서버 제목 변경은 그림판에서 유효한 편집 세션으로 진행한다. |
| 작품 열기 | `/drawing/:artworkId` → `useArtwork` → UID와 작품 ID 복합 키. `?view=server`는 확정 버전의 PNG를 인증된 API에서 받아 읽기 전용으로 표시한다. 기존 로컬 작업본과 대기열은 보존한다. |
| 그림판·레이어 | `DrawingSpace` → `DrawCanavs`, `useCanvasPersistence`, `useLayers`, `layerRepository`. 작업 대상은 `layerId`, 표시 순서는 `sortOrder`다. CSS 배경과 투명 PNG는 독립적이다. 원본 Canvas는 IndexedDB의 작품 크기를 사용하고 줌은 표시 크기만 바꾼다. 다시 열면 존재하는 첫 레이어를 선택한다. 선택 자체를 작품 메타데이터에 저장하는 기능은 없다. |
| 저장·권한 | 로컬 저장은 PNG·레이어와 대기열을 트랜잭션으로 기록한다. `useArtworkSync`는 로컬 저장, 대기, 업로드, 실패, 서버 확정을 구분한다. `useEditSession`, `editSessionService`, Cloud Functions가 권한과 서버 버전·세대를 확인한다. 명시적 편집 종료는 로컬 저장·동기화·확정 확인을 거쳐 세션을 반납한다. |
| 초안·이력 | `RecoveryDrafts`는 UID별 IndexedDB 초안을 표시한다. `ArtworkHistory`는 확정된 수정 이력만 서버 API로 조회한다. 서버 확정본 보기와 초안 내역은 별도 경로다. |
| 서비스 환경 | `firebaseEnvironment` → 같은 Firebase 앱의 Auth·Firestore·Storage·Functions. 개발 기본 연결은 루프백이다. 운영 모드는 승인된 명시적 설정이 필요하고 Functions 진입점은 Emulator에서만 업무 함수를 노출한다. |

메인 사용자 경로는 **가입과 프로필 저장 → 로그인 → 작품 목록 → 그림판과 레이어 편집 → 로컬 저장 → 서버에 저장과 편집 세션 → 서버 동기화 → 작품 목록 또는 명시적 편집 종료**다. 로그아웃 후 목록은 로그인으로 이동한다. 그림판 URL을 직접 열면 UID, 작품 유무와 접근 권한을 확인한다.

실제 렌더링 경로에서 `dummyData.js`의 작품·레이어 임포트는 발견되지 않았다. 작품 카드에서 미리보기 필드가 없으면 기존의 빈 미리보기를 표시한다. 선택 도구의 실질적인 객체 편집, 작품 썸네일 생성과 AI 기능은 현재 DB 연결 검증 범위에 포함되지 않는다.

## 9-B/C 수정과 품질 점검

- **다운로드가 늦게 끝나면서 페이지가 바뀌는 오류.** 서버 PNG 응답을 막은 상태에서 목록을 떠났다가 응답을 풀자 기존 코드가 다시 서버 작품으로 이동했다. 목록이 닫히거나 UID가 전환되면 진행 중인 작품 열기를 취소한다. 취소 신호를 이미지 요청과 IndexedDB 설치의 접근 검사에 전달해 늦은 이동과 캐시 설치를 막는다. 이미 완료된 정상 다운로드와 기존 서버 버전·UID 검증은 그대로 사용한다.
- **컬러 피커 렌더링과 lint 경고.** 부모 HEX 값이 바뀔 때 effect가 HSV를 다시 설정하던 흐름을 정리했다. 입력 중인 색상의 HSV를 유지하며 외부 HEX가 달라지면 렌더 시 반영한다. 툴바의 미사용 `useRef` 임포트를 제거했다. CSS 및 도구 버튼 구성은 그대로 사용한다.
- **구독과 비동기 작업.** 로컬 작품 조회는 UID·조건을 키로 이전 결과를 가리고 Dexie 구독을 해제한다. Firestore의 일회성 서버 조회는 성공·실패·시간 초과 후 구독을 닫는다. Canvas는 경로 전환 시 타이머·렌더러·이벤트를 정리하고 그림판 이동 전 보류된 저장을 완료한다. 서버 동기화 서비스는 같은 작품의 중복 요청을 공유하고 서버 영수증으로 반복 확정을 차단한다. Canvas의 `contextlost` 리스너는 렌더 시 교체되며 직전 리스너를 해제한다. 프레임 속도와 메모리 사용량은 별도로 측정하지 않았다.
- **번들 경고.** Vite의 메인 미니파이 JS 청크는 약 1,066 kB, gzip은 약 327 kB로 500 kB 경고 기준을 넘는다. 주요 의존성은 Firebase 웹 SDK, React/Router와 Dexie다. 단계 9에서는 저장·라우팅 검증에 집중하고 빌드 분할 구조는 유지했다.

| 변경 파일 | 역할 |
| --- | --- |
| `src/page/ArtworkList.jsx`, `src/services/artworkSyncService.js` | 목록 이동 뒤 지연된 다운로드·탐색 취소 |
| `src/components/DrawingSpace/Color.jsx`, `ToolPicker.jsx` | 색상 상태 동기화 중복과 미사용 임포트 정리 |
| `scripts/test-artwork-metadata.mjs`, `test-canvas-persistence.mjs` | 미로그인 직접 그림판 경로, 브라우저 앞으로 가기, 모바일 화면 터치 PNG 검증 |
| `scripts/test-artwork-sync.mjs`, `test-offline-recovery.mjs` | 지연 다운로드 취소 재현, 오프라인 화면 이동 중 세션·대기열 유지 검증 |

지연 다운로드는 수정 전 검사에서 재현했고 수정 후 통과했다. 처음 확장 검사는 브라우저 앞으로 가기 전 필요한 기록과 화면 재진입 후 레이어 패널 열기가 빠져 각각 시간 초과됐다. 두 테스트의 준비 단계를 수정해 Canvas 35개와 오프라인 12개를 각각 다시 실행했다.

- **미검증.** 실제 휴대폰·펜·기기 두 대, Edge 외 브라우저, 실제 저장 공간 고갈과 강제 종료 복구율, 대규모 작품의 성능 계측, 운영 Firebase 연결과 IAM, Node.js 22 운영 런타임은 미검증이다. 현재 자동 검사는 로컬 Node.js 24.20.0과 Edge의 분리된 브라우저 프로필에서 실행했다.

### 운영 전 남은 작업

1. npm 감사의 개발 도구 패치와 Firebase 의존성 호환성을 별도 변경으로 검증한다.
2. 팀에서 추가 UI를 선택한다면 위 브랜치 중 필요한 변경의 범위를 정한 뒤 입력·저장 콜백과 권한을 다시 검증한다.
3. 승인 이후 별도 운영 Functions 진입점, 실제 프로젝트·버킷과 서비스 계정, 운영 규칙·색인·HTTPS 오리진을 준비한다. 운영 연결 이후 실제 기기 두 대에서 같은 절차를 재검증한다.

작업 중 기존 DB 스키마·규칙, 의존성 및 CSS를 수정하지 않았다. 사용자의 작품·초안·대기열을 보존했으며, 검사는 로컬 테스트 데이터만 사용했다. Firebase 운영 연결·활성화·배포와 Git 커밋·푸시는 실행하지 않았다.

## 직접 확인

1. 기존 Emulator 실행 상태에서 `npm.cmd run dev -- --host 127.0.0.1`로 앱을 띄운다. 브라우저에서 터미널이 표시한 루프백 주소를 연다. 기존 로컬 작품 확인 시 사용하던 포트를 유지한다.
2. 테스트 계정을 만들어 로그인한 뒤 작품을 만든다. 레이어를 추가하고 투명 영역을 남겨 그림을 그린다. 로컬 저장 표시 후 뒤로·앞으로 이동하고 새로고침하여 그림이 복원되는지 확인한다.
3. 새 작품을 서버에 등록한다. 분리된 Edge 프로필 B에서 같은 계정으로 서버 작품을 연다. A가 편집 중일 때 B의 쓰기 제한, A의 명시적 종료 후 B의 세션 획득을 확인한다.
4. A가 세션을 가진 테스트 작품을 열어 오프라인 상태로 그린 뒤 목록으로 나갔다 재진입한다. B에서 강제 복구를 수행하고 새 그림을 서버에 확정한다. A를 다시 온라인으로 바꾼 뒤 B의 서버 확정본과 A의 로컬 초안이 구분되는지 확인한다.
5. 자동 검사는 `scripts/test-*.mjs`를 Playwright와 로컬 Emulator 환경에서 실행한다. 운영 전 준비는 [8단계 문서의 승인 후 순서](./8단계_운영환경_준비.md#운영-활성화-승인-후-순서)를 따른다.
