# 문서 개요

**프로젝트:** 모바일 드로잉 애플리케이션 AI 기반 지능형 인터페이스 (IntelligentCanvas)  
**문서 성격:** DB 담당자용 구현 기준 계획서 (설계 문서, 구현 완료 보고서 아님)  
**개정 기준:** 기존 「DB구축 계획(1).pdf」 및 프로젝트 전체 계획서, 이후 합의한 충돌 방지 정책  
**현재 개발 상태:** React 프론트엔드 일부 구현, `database` 브랜치 준비, Firebase Auth·Firestore Emulator 실행 확인. **React SDK 연동·로컬 저장·서버 저장 및 충돌 방지 구현은 검증 완료 상태가 아님.**

## 개정 핵심 결정

| 항목 | 기존 DB 초안 | 본 개정본의 확정 정책 |
|---|---|---|
| 닉네임 | 고유 닉네임 예약(`nicknameClaims`) | **중복 허용**, UID만 고유 식별자로 사용 |
| 충돌 처리 | 작품 버전 불일치 시 충돌 복사본 | **작품별 단일 편집 세션**이 1차 차단, 버전 검사로 2차 방어 |
| 세션 적용 범위 | 초기 초안에는 명시적 잠금 없음; 후속 논의에서 계정당 1개 제안 | **작품당 1개**. 서로 다른 작품은 각 기기에서 편집 가능 |
| 오프라인 | 로컬 편집 및 추후 동기화 | **온라인에서 발급받은 기존 권한으로만 오프라인 편집** |
| 기기 전환 | 버전 불일치 및 충돌 복사본 중심 | **완전 동기화 → 명시적 세션 반납 → 다음 기기에서 이력 확인 후 권한 획득** |
| 강제 복구 | 별도 절차 없음 | 서버 세션 세대(`generation`) 증가, 기존 요청 차단, 로컬 초안 보존 |
| 수정 이력 | 레이어 파일 리비전/버전 관리 | **A 방식: 수정 내용·대상 레이어·시각·버전 목록만 표시** |
| 저장 모델 | IndexedDB, Firestore, Storage | 유지. **PNG와 편집 객체 JSON을 분리** |

> **우선순위:** 이 문서의 확정 정책이 기존 PDF의 닉네임 예약 및 단순 버전 충돌 방식과 다를 경우, **본 개정본을 우선**한다. 이전 버전 이미지 비교·자동 병합·과거 캔버스 복원 UI는 초기 범위에 포함하지 않는다.

# 1. 목표 및 범위

React 기반 웹/PWA 드로잉 앱에서 사용자 정보, 작품, 레이어, 픽셀 그림, 편집 가능한 객체, AI 제안을 보존하고 여러 기기에서 이어서 그릴 수 있도록 한다. 저장은 **로컬 우선**으로 처리하고 서버 사본은 별도로 동기화한다.

**설계 목표**

1. 작업 중 새로고침이나 일시적 오프라인 상태에서도 로컬 그림을 복원한다.
2. 동일 계정의 **같은 작품**에는 동시에 하나의 편집 세션만 허용한다.
3. 같은 계정이 **서로 다른 작품**을 서로 다른 기기에서 편집하는 것은 허용한다.
4. 온라인에서 발급한 세션을 보유한 기기는 오프라인에서도 계속 편집한다.
5. 서버 저장은 소유권·세션·세대 번호·작품 버전 검사를 통과한 경우에만 확정한다.
6. 정상적인 기기 전환과 강제 복구를 구별하며, 미동기화 작업을 가능한 범위에서 보존한다.
7. 서버에 확정된 수정 내역을 **문자 목록**으로 표시하고, 사용자 확인 후 이어서 편집한다.
8. AI 결과는 사용자 승인 후 일반 편집 데이터로 반영한다.

**초기 범위 제외:** 동시 공동 편집(CRDT/OT), 오프라인에서 새로운 서버 편집 권한 발급, 두 기기의 자동 병합, 버전별 그림 비교 화면, 자동 과거 버전 복원, 전량 펜 획 이력 보존.

# 2. 기술 구성과 역할

| 구성 요소 | 선택 기술 | 책임 범위 |
|---|---|---|
| UI·드로잉 | React + Vite | 작품 목록, 캔버스, 레이어 UI, 상태 및 수정 이력 목록 |
| 로컬 DB | IndexedDB + Dexie | PNG Blob, 객체 JSON, 로컬 버전, 동기화 대기열, 편집 권한 캐시, 복구 초안 |
| 사용자 인증 | Firebase Authentication | 이메일·비밀번호 인증, UID 확인, 비밀번호 재설정 |
| 클라우드 메타데이터 | Cloud Firestore | 사용자·작품·레이어, 현재 세션, 서버 버전, 수정 이력 |
| 클라우드 파일 | Cloud Storage for Firebase | `raster.png`, `objects.json`, 썸네일, 프로필 이미지 |
| 서버 권한 제어 | Firebase Cloud Functions | 세션 발급·반납·강제 복구, 업로드 확정, 버전 검사 |
| 오프라인 앱 실행 | PWA Service Worker | 정적 리소스 캐시 및 재실행 지원(별도 구현) |
| AI 처리 | 인증된 AI API | 레이어 분류·이름 제안, OCR, 도형·선·화살표·표 변환 제안 |

**원칙:** Firestore 문서에는 거대한 그림 Blob이나 늘어나는 객체 배열을 직접 넣지 않는다. 파일은 Storage에, 로컬 원본과 대기열은 IndexedDB에 둔다. Firebase 구성 파일과 보안 규칙은 Git으로 관리하고, 실제 비밀키·서비스 계정 자격증명과 개인용 `.env.local`은 커밋하지 않는다.

# 3. 작품 및 레이어 데이터 계약

DB 구현 전 프론트엔드 팀과 **캔버스 좌표계, PNG 투명도, 객체 JSON 구조, 렌더 순서, ID·버전 규칙**을 합의한다. 현재 프론트엔드가 미완성이므로 실제 저장 객체 형태는 컴포넌트 분석 후 확정한다.

| 단위 | 필드 또는 파일 | 설명 |
|---|---|---|
| 작품 | `artworkId`, `ownerUid`, `title`, `titleNormalized` | 작품 식별자 및 검색 표시 |
| 크기 | `widthPx`, `heightPx`, `dpi`, `displayUnit` | 실제 좌표는 픽셀, DPI와 단위는 출력·표시용 |
| 작품 상태 | `state`, `completedAt`, `deletedAt`, `thumbnailPath` | 활성/삭제, 완성 여부, 미리보기 |
| 서버 버전 | `serverVersion`, `schemaVersion`, `createdAt`, `updatedAt` | 저장 충돌 및 호환성 기준 |
| 레이어 메타 | `layerId`, `name`, `sortOrder`, `opacity`, `visible`, `isTemporary`, `category` | 화면의 레이어 관리 정보 |
| 레이어 내용 | `raster.png` | 투명 배경 픽셀 이미지(Blob) |
| 편집 객체 | `objects.json` | 텍스트·도형·선·화살표·표의 종류, 좌표, 변형, 스타일, 순서 |
| 레이어 파일 참조 | `currentRevisionId`, `pngPath`, `objectsPath`, `formatVersion` | 현재 서버에서 확정된 버전 참조 |

**렌더링·편집 계약(원본 계획 유지):** 아래 레이어부터 위 레이어 순서대로 합성한다. 같은 레이어 안에서는 객체를 먼저, 픽셀을 나중에 그리는 규칙을 기본안으로 삼되 프론트엔드 실제 렌더러와 일치시켜 확정한다. 배경색은 작품 속성으로 분리한다. OCR·벡터 변환 승인 시 대상 픽셀 제거와 새 객체 추가를 **하나의 로컬 편집 작업**으로 확정한다. 변환 전 내용은 최소한 복구 가능 기간 동안 유지한다.

**레이어 분류값:** `선화`, `채색`, `배경`, `텍스트`, `명암`; 아직 분류하지 않은 레이어는 `null`. 사용자에게 보이는 이름과 실제 ID를 분리한다. 텍스트 객체는 폰트 식별자, 크기, 정렬, 줄바꿈 규칙을 포함한다.

# 4. 논리 데이터 모델 및 Firestore 구조

## 4.1 논리 관계

```text
USER(uid) 1 ── N ARTWORK(artworkId)
ARTWORK  1 ── N LAYER(layerId)
ARTWORK  1 ── 1 EDIT_SESSION(current)
ARTWORK  1 ── N ARTWORK_REVISION(revisionId)
LAYER    1 ── N LAYER_CONTENT(contentRevisionId)
LAYER_CONTENT 1 ── N DRAW_OBJECT(objectId, JSON 내 배열)
```

`NICKNAME_CLAIM` 개체는 **삭제**한다. 동일한 닉네임을 서로 다른 UID가 사용할 수 있으며 닉네임의 변경은 소유권이나 저장 경로에 영향을 주지 않는다.

## 4.2 Firestore 추천 경로

```text
users/{uid}
  nickname, avatarPath, featuredArtworkId, aiSettings, createdAt, updatedAt

users/{uid}/artworks/{artworkId}
  ownerUid, title, titleNormalized, widthPx, heightPx, dpi, displayUnit,
  backgroundColor, state, completedAt, deletedAt, thumbnailPath,
  serverVersion, schemaVersion, createdAt, updatedAt

users/{uid}/artworks/{artworkId}/layers/{layerId}
  name, sortOrder, opacity, visible, isTemporary, category,
  currentRevisionId, pngPath, objectsPath, formatVersion, updatedAt

users/{uid}/artworks/{artworkId}/editSession/current
  sessionId, deviceId, generation, status, startedAt, lastSeenAt, updatedAt

users/{uid}/artworks/{artworkId}/revisions/{revisionId}
  serverVersion, requestId, sessionId, deviceId, changeType,
  changedLayers, summary, createdAt
```

**주의:** 위 경로의 `editSession`과 `revisions`는 서브컬렉션이며 `current`는 문서이다. `ownerUid`와 상위 경로의 UID가 동일한지 서버에서 확인한다. 계정별 독립 데이터이며 다른 사용자 작품은 기본적으로 비공개다.

## 4.3 Storage 추천 경로

```text
users/{uid}/artworks/{artworkId}/layers/{layerId}/{contentRevisionId}/raster.png
users/{uid}/artworks/{artworkId}/layers/{layerId}/{contentRevisionId}/objects.json
users/{uid}/artworks/{artworkId}/thumbnails/{thumbnailRevisionId}.png
users/{uid}/profile/{avatarRevisionId}.png
```

확정된 파일을 **같은 경로로 덮어쓰지 않는다.** 파일을 먼저 새 경로에 올리고, 그 후 서버가 검증을 완료하면 Firestore의 `currentRevisionId`와 경로 참조를 원자적으로 갱신한다. 수정 이력의 `revisionId`(작품 저장 이벤트)와 개별 레이어의 `contentRevisionId`(내용 파일 버전)는 역할을 구분한다.

# 5. 닉네임·인증·접근 제어

1. 가입·로그인 및 비밀번호 재설정은 Firebase Auth에서 처리한다. 비밀번호는 Firestore에 저장하지 않는다.
2. `users/{uid}` 문서의 `nickname`은 **표시용 값**이며 중복을 허용한다. 닉네임 예약 컬렉션, 고유성 검사, 중복 가입 차단 트랜잭션은 구현하지 않는다.
3. 작품·레이어·썸네일·프로필 파일의 접근은 **인증된 UID와 작품 소유권**으로 제한한다.
4. 편집 세션, 서버 버전, 서버에 확정된 수정 이력, 현재 파일 참조는 **서버 함수만 수정**하도록 제한한다. 클라이언트의 직접 쓰기로 보호 필드가 변경되지 않도록 Rules를 작성한다.
5. Cloud Functions의 Admin SDK는 Security Rules를 우회할 수 있으므로 서버 함수 내부에서 **UID·소유권·세션·요청 입력**을 재검증한다.
6. AI API는 ID 토큰, 작품 소유권 및 기준 버전을 검사한다. 오래된 모델 제안은 자동 적용하지 않는다.
7. 로그인 UID가 변경되면 이전 계정의 동기화 대기열을 중단한다. 미동기화 데이터는 자동 삭제하지 않고 계정별로 구분한다.

# 6. 작품별 단일 편집 세션 및 충돌 방지

## 6.1 핵심 정책

- **잠금 단위는 계정이 아니라 작품(`artworkId`)**이다. A가 `pic`을 편집하는 동안 B는 `pic`을 읽기 전용으로 열 수 있지만, 별개인 `cat` 작품은 편집할 수 있다.
- **새 세션 획득은 온라인에서만** 허용한다. 서버가 Firestore 트랜잭션으로 기존 활성 세션 유무를 확인한 후 한 요청에만 권한을 준다.
- 현재 세션을 획득한 기기는 네트워크가 끊겨도 오프라인에서 로컬 작업을 이어간다. 오프라인 전환만으로 세션을 해제하거나 자동 만료하지 않는다.
- 인터넷 재연결 후 **동기화만 완료해서는 세션이 해제되지 않는다.** 사용자가 명시적으로 종료하고 동기화·검증이 성공한 경우에 서버가 권한을 반납한다.
- 탭 닫기나 브라우저 비정상 종료는 세션 반납을 보장할 수 없으므로 **강제 복구 절차**를 별도로 둔다.
- 같은 기기의 여러 탭도 동일 작품을 동시에 편집하지 못하게 `Web Locks API` 또는 `BroadcastChannel` 기반 로컬 조정을 추가한다. 로컬 잠금은 서버 검증을 대체하지 않는다.

## 6.2 세션 문서 필드

| 필드 | 의미 | 관리 규칙 |
|---|---|---|
| `sessionId` | 서버가 발급한 무작위 세션 식별자 | 작업 중인 기기에서만 보관 |
| `deviceId` | 기기 구별용 비밀이 아닌 식별자 | 인증 수단으로 간주하지 않음 |
| `generation` | 해당 작품의 세션 세대 번호 | 강제 복구 때 증가, 서버가 단조 증가 유지 |
| `status` | `active` / `released` | 서버 권한 상태 |
| `startedAt` | 세션 발급 시각 | 서버 시각 기록 |
| `lastSeenAt` | 마지막 온라인 확인 | 단순 상태 표시용, 오프라인 자동 해제 조건 아님 |
| `updatedAt` | 마지막 상태 변경 | 서버 시각 기록 |

## 6.3 서버 API 계약

| 함수(가칭) | 호출 목적 | 핵심 검사 |
|---|---|---|
| `acquireArtworkSession(artworkId)` | 온라인 편집 권한 획득 | UID·소유권·활성 세션·트랜잭션 |
| `getArtworkSession(artworkId)` | 현재 편집 상태 조회 | UID·읽기 권한 |
| `commitArtworkRevision(payload)` | 서버 저장 확정 | UID·`sessionId`·`generation`·`expectedServerVersion`·`requestId` |
| `releaseArtworkSession(artworkId, sessionId, ...)` | 정상 편집 종료 | 동일 세션·최종 서버 확정 버전 확인 |
| `forceRecoverArtworkSession(artworkId)` | 예외적 강제 복구 | 소유권·명시적 동의·재인증 정책·세대 증가 |
| `getArtworkHistory(artworkId)` | 서버 수정 이력 목록 | UID·읽기 권한·페이지 처리 |

새 저장 요청은 서버의 현재 `sessionId`와 `generation`이 일치하고 `expectedServerVersion`이 서버의 `serverVersion`과 같을 때만 확정한다. 버전 불일치나 권한 무효화가 발생하면 **자동 덮어쓰기·자동 병합을 하지 않는다.** 클라이언트는 해당 작업을 복구 가능한 상태로 보존한다.

## 6.4 명시적 예외: 강제 복구의 한계

A가 오프라인인 동안 B가 강제 복구하면 B가 **새 세대 번호**로 서버 편집권을 획득할 수 있다. A는 오프라인인 동안 그 사실을 알 수 없어 로컬 작업을 계속할 수 있지만, 다시 온라인이 되면 A의 옛 세대 번호를 가진 저장 요청은 서버에서 반드시 거부된다. 따라서 보장하는 것은 **서버 작품의 충돌성 덮어쓰기 방지**이지, 두 오프라인 기기에서 동시에 로컬 수정이 존재할 가능성까지 없애는 것은 아니다.

# 7. IndexedDB 구조와 로컬 자동 저장

## 7.1 Dexie 저장소

| 저장소 | 주요 키/색인(제안) | 주요 데이터 |
|---|---|---|
| `profiles` | `uid` | 현재 사용자 표시 정보 |
| `artworks` | `[uid+artworkId]`, `[uid+state+updatedAt]` | 로컬 작품 목록 및 메타데이터 |
| `layers` | `[uid+artworkId+layerId]`, `[uid+artworkId+sortOrder]` | 레이어 정보 |
| `layerContents` | `contentRevisionId`, `[uid+artworkId+layerId]` | PNG Blob·객체 JSON·로컬 버전 |
| `editGrants` | `[uid+artworkId]` | `sessionId`, `generation`, 로컬 상태 |
| `syncQueue` | `requestId`, `[state+nextRetryAt]`, `[uid+artworkId]` | 동기화 작업·재시도·기준 서버 버전 |
| `recoveryOps` | `[uid+layerId+sequence]` | 일시 복구 기록 |
| `recoveryDrafts` | `draftId`, `[uid+artworkId]` | 무효화·충돌 시 보존한 로컬 스냅샷 |
| `aiProposals` | `proposalId`, `[uid+artworkId]` | AI 제안·승인 여부·대상 버전 |

Dexie 스키마 버전은 앱의 로컬 DB 버전과 별도로 관리한다. 서버의 `schemaVersion`과 PNG·객체의 `formatVersion`도 서로 독립적으로 관리한다.

## 7.2 저장 절차

1. 획 입력 종료 또는 객체 편집 완료 시 짧은 복구 기록을 보존한다. 창 닫기 이벤트에만 의존하지 않는다.
2. 변경된 레이어의 PNG 인코딩과 객체 JSON 생성이 끝나면 **하나의 IndexedDB 트랜잭션**에서 콘텐츠 스냅샷·레이어 로컬 버전·`syncQueue` 항목을 함께 확정한다.
3. UI는 **'기기에 저장됨'**과 **'서버 동기화 완료'**를 별도 상태로 표시한다.
4. 사용자의 계속된 편집으로 업로드 도중 새로운 로컬 버전이 생겨도 이전 버전 스냅샷과 대기열을 덮어쓰지 않는다.
5. 로컬 저장 실패(용량 부족·권한 제한·브라우저 오류)는 성공으로 표시하지 않는다. 명시적 오류 메시지와 재시도/내보내기 안내를 제공한다.

**성능 목표(초기 목표, 보장 아님):** 완성된 편집의 로컬 복구 기록은 1초 이내 저장을 목표로 하고, 편집 후 1·3·5·10초에 강제 종료하는 시나리오에서 복구 여부를 측정한다. IndexedDB도 사용자의 브라우저 데이터 삭제나 저장 공간 부족에서 영구 보장을 제공하지 않는다.

# 8. 서버 동기화·버전 확정·정상 종료

## 8.1 동기화 알고리즘

1. 로컬 `syncQueue`의 동일 작품 작업을 순서에 맞게 직렬 처리한다. 연속 펜 편집은 안전한 범위에서 묶어 업로드 횟수를 줄인다.
2. 서버의 현재 세션 ID·세대 번호·버전을 확인한다. 무효화된 세션이면 업로드 또는 서버 확정을 즉시 중지한다.
3. 변경된 레이어의 PNG·JSON만 새 **불변 Storage 경로**에 업로드한다. 이름·순서·불투명도만 바뀐 경우 이미지 업로드는 생략할 수 있다.
4. 서버 함수가 업로드된 경로·소유권·파일 형식·크기 등을 검증한다.
5. **Firestore 트랜잭션**에서 현재 세션과 `expectedServerVersion`을 재확인하고, 레이어 파일 참조·작품 버전 증가·수정 이력 문서·`requestId` 처리 기록을 함께 확정한다.
6. 성공 확인된 **해당 로컬 버전까지만** 동기화 완료 처리한다. 이후 변경은 별도 대기 작업으로 유지한다.
7. 실패 시 기존 서버 참조는 보존한다. 업로드만 되고 확정되지 않은 파일은 보존·백업 정책을 고려하여 유예 기간 후 정리한다.

**멱등성:** 네트워크 재시도로 동일한 `requestId`가 반복되더라도 작품 버전과 이력이 중복 확정되지 않도록 서버 저장 요청 기록을 둔다. `requestId`의 결과가 이미 확정되었으면 동일 결과를 반환한다.

## 8.2 편집 종료 및 다른 기기로 이동

정상 편집 종료는 **새 입력 중단 → 로컬 저장 완료 → 모든 미동기화 작업 전송 → 서버 확정 확인 → 세션 반납 → 화면 읽기 전용 전환** 순서이다. 세션을 먼저 놓은 뒤 나머지 그림을 보내는 흐름은 금지한다.

서버는 클라이언트의 로컬 IndexedDB를 직접 볼 수 없으므로, 클라이언트는 종료 시점의 로컬 버전·대기열 상태를 확인하고 마지막 확정 버전을 전달해야 한다. 동기화 실패 또는 오프라인에서는 종료 완료를 표시하지 않고 현재 세션을 유지한다.

B에서 이어서 편집할 때는 **최신 서버 메타데이터와 수정 이력을 보여주고, 사용자 확인 → 서버에서 다시 권한 획득 → 최신 작품 다운로드** 순서로 처리한다. 이력 화면을 보는 동안 타 기기가 권한을 얻을 수 있으므로 확인 버튼을 눌렀을 때 권한을 다시 검사한다.

# 9. 수정 이력 A 방식: 내용 목록만 표시

## 9.1 저장 및 표시 데이터

| 필드 | 설명 |
|---|---|
| `revisionId` | 작품 서버 저장 이벤트 고유 ID |
| `serverVersion` | 저장 확정 후 작품 버전 |
| `requestId` | 중복 저장 방지 키 |
| `sessionId`, `deviceId` | 변경을 확정한 편집 세션 식별 |
| `changeType` | `artwork_created`, `layer_added`, `layer_modified`, `layer_deleted`, `layer_reordered`, `artwork_updated` 등 |
| `changedLayers` | 변경된 레이어 ID·표시 이름 목록 |
| `summary` | 예: "채색 레이어 수정", "배경 레이어 추가" |
| `createdAt` | 서버에서 확정된 시각 |

**A 방식의 범위:** 버전·변경 내용·수정 시각의 **텍스트 목록**을 표시한다. 과거 그림 미리보기·전후 이미지 비교·과거 버전 복원 버튼은 구현하지 않는다. 기존 레이어 PNG의 `contentRevisionId`는 파일 안전성과 백업·정리에 사용되며, **과거 이미지 표시 기능과 동일하지 않다.**

사용자가 펜을 움직일 때마다 이력을 기록하지 않고 **한 번의 서버 저장 확정** 단위로 의미 있는 요약을 기록한다. 클라이언트는 실제 레이어 작업 이벤트를 전달하며 서버가 형식·범위를 검증한다. 별도 컴퓨터 비전으로 '무엇을 그렸는지' 자동 해석하는 기능은 초기에 포함하지 않는다.

## 9.2 표시 예시

```text
pic - 최근 수정 이력
v4  채색 레이어 수정       15:40
v3  선화 레이어 수정       15:25
v2  배경 레이어 추가       15:10
v1  작품 생성             14:50

[읽기 전용으로 보기]  [최신 버전에서 이어서 편집]
```

아직 서버에 확정되지 않은 A 기기의 오프라인 변경은 B의 수정 이력 목록에 나타나지 않는다.

# 10. 강제 복구 및 복구 초안

1. 기기 B에서 기존 세션이 활성 상태인 작품을 열면 읽기 전용과 **강제 복구** 선택지를 표시한다.
2. 강제 복구는 기존 기기가 고장·분실되어 정상 반납이 불가능한 예외 상황에만 사용하도록 경고한다.
3. 강제 복구 전에 **기존 기기의 미동기화 데이터는 서버에 없을 수 있음**을 안내하고 사용자의 명시적 승인을 받는다. 위험도에 따라 재인증을 적용한다.
4. 서버가 UID·소유권을 확인한 뒤 트랜잭션으로 `generation`을 증가시키고 B에 새 `sessionId`를 발급한다. 복구 실행 결과는 감사 기록으로 남긴다.
5. 구세대 A의 `commitArtworkRevision`·세션 반납 요청은 거부한다. 서버의 최신 작품·수정 이력은 유지한다.
6. A가 재접속해 권한 무효화를 알게 되면 자동 동기화를 중단하고 미동기화 로컬 내용을 `recoveryDrafts`에 보존한다. 가능하면 내보내기 기능을 제공한다.
7. B는 마지막 서버 확정 버전부터 편집한다. A의 오프라인 작업과 B의 작업을 **자동 병합하지 않는다.**

**제약:** 고장·분실된 A 기기에만 존재하는 로컬 파일을 서버나 B가 임의로 회수할 수는 없다. 브라우저 저장소가 삭제된 경우도 동일하다. 복구 초안 보존은 그 기기에서 로컬 데이터에 다시 접근할 수 있을 때만 가능하다.

# 11. 작품 관리·AI 기능 연동

## 11.1 작품 목록, 검색, 삭제, 복제

- 작품 목록 조회: 사용자 소유 작품의 `state`, `updatedAt` 기준 정렬 및 페이지 처리. 처음에는 사용자당 수백 작품 규모를 가정하고 로컬 메타데이터 동기화 후 제목 부분 검색을 적용한다.
- 작품 삭제: 즉시 파일을 물리 삭제하지 않고 `state = deleted`, `deletedAt` 삭제 표식(tombstone)을 서버에 확정해 오래 오프라인이던 기기의 잘못된 재생성을 막는다. 실제 파일 정리는 보존 기간 이후 별도로 실행한다.
- 작품 복제: 새로운 `artworkId`, 레이어 ID, 독립 파일 참조를 생성한다. 복제본 수정이 원본을 변경해서는 안 된다.
- 작품 수정(이름·크기·삭제 등): 서버 상태 변경은 현재 작품의 편집 권한/버전 규칙을 따라야 한다. 읽기 전용에서 수정 가능한 우회 경로를 만들지 않는다.

## 11.2 AI 데이터 계약

원본 프로젝트 계획서의 레이어 자동 분류·레이어 이름 제안·오분류 경고·임시 레이어 분리·손글씨 OCR·도형/선/화살표/표 벡터화를 유지한다. `aiProposals`에는 **대상 레이어, 기준 내용 버전, 제안 종류, 모델 버전, 승인·거절 상태**를 보관한다.

AI는 **제안 → 사용자 확인 → 적용** 순서를 지키며, 승인한 변경만 일반 로컬 편집 및 서버 동기화 경로로 저장한다. 승인 전 원본은 보존하고 오래된 작품 버전을 대상으로 생성된 AI 제안은 무조건 덮어쓰지 않는다. AI 제안의 상세 영구 분석 DB는 초기 범위에서 제외한다.

# 12. 인덱스·버전·마이그레이션

| 대상 | 초기 인덱스/규칙 |
|---|---|
| Firestore 작품 목록 | `state + updatedAt DESC` (필요 시 복합 인덱스) |
| Firestore 수정 이력 | 작품 하위 `revisions`에서 `createdAt DESC` 또는 `serverVersion DESC` |
| Firestore 레이어 목록 | 작품 하위 `layers`의 `sortOrder` |
| IndexedDB 작품 | `[uid+state+updatedAt]` |
| IndexedDB 레이어 | `[uid+artworkId+sortOrder]` |
| IndexedDB 대기열 | `[state+nextRetryAt]`, `[uid+artworkId]` |
| IndexedDB 복구 기록 | `[uid+layerId+sequence]` |

`schemaVersion`(문서 구조), Dexie DB 버전(로컬 저장소), `formatVersion`(PNG·객체 묶음)을 서로 구분한다. 구버전에서 신버전으로 이동할 때 **로컬 DB를 삭제하고 다시 만들지 않는다.** 특히 서버에 없는 Blob·복구 기록·대기열을 보호해야 한다. PWA의 오래된 탭이나 서비스 워커가 남는 경우도 고려한다.

# 13. 개발 환경·운영·백업·비용

| 환경 | 구성 |
|---|---|
| 로컬 개발 | `IntelligentCanvas` + Firebase Emulator Suite(Auth, Firestore; Storage·Functions는 해당 단계에서 추가) + IndexedDB |
| 팀 개발 | Firebase 개발 프로젝트·개발 AI 서버 등 운영과 분리된 테스트 환경 |
| 운영 | 운영 Firebase 프로젝트·Storage 버킷·AI 서버·서비스 계정, 접근 권한 별도 관리 |

**현재 확인된 개발 진행 상황(2026-11-16 기준):** GitHub `database` 브랜치와 Firebase 설정 파일은 통합되었고 Auth 9099, Firestore 8080, UI 4000의 Emulator 실행을 확인했다. React의 Firebase SDK 연결·데이터 저장/조회·Storage·Functions·작품별 편집 세션은 이후 구현 및 테스트가 필요하다. 실제 프론트엔드는 메인/그림판 일부가 있는 미완성 상태로 보고 연동 범위를 제한한다.

**운영·복구 기본안(원본 계획의 제안, 미설정 상태):** Firestore 일일 백업과 일정 보관기간, Storage 현재 파일 및 백업이 참조할 수 있는 이전 파일 보존, Storage 삭제 사고 대비 복구 정책, Firebase Auth 계정 내보내기, Rules·인덱스·마이그레이션 Git 관리, 실제 복구 연습을 함께 설계한다. 예시 목표인 백업 기준 최대 24시간의 서버 데이터 손실/1일 내 복구는 테스트로 검증해야 하며, 확정된 SLA가 아니다. Firestore 백업만 복구해도 Storage와 Auth가 자동 복구되는 것은 아니다.

**용량·비용 유의:** 전체 PNG 저장은 초기 구현이 단순하지만 큰 캔버스/많은 레이어에서 인코딩 비용과 메모리 사용량이 증가한다. 먼저 전체 PNG 방식으로 시작하되 대표 모바일 기기에서 측정한다. 로컬 저장은 자주, 서버 업로드는 안전하게 묶어서 수행한다. 저장 지역·다운로드 횟수·Storage 업로드·AI 호출량 등을 측정한 뒤 예산을 정하고 클라우드 서비스를 활성화한다. 브라우저의 영속 저장 요청은 사용자 데이터 삭제를 방지하지 못한다.

# 14. 구현 순서: 미완성 프론트엔드와 병행 개발

| 단계 | DB 담당 구현 내용 | 완료 판정 |
|---|---|---|
| 1. 코드·데이터 계약 분석 | 현재 메인/그림판 구조 분석, PNG/JSON 계약, 변경 파일·연동 지점 파악 | 기존 UI 손상 없이 데이터 형식 합의 |
| 2. Firebase SDK·테스트 | 기존 프로젝트 Emulator 연결, 인증·Firestore 로컬 저장 테스트 | 테스트 문서를 저장·조회하고 운영 DB 미접근 확인 |
| 3. Dexie 로컬 DB | 작품·레이어·Blob·객체·syncQueue, 자동 저장 및 복구 | 그림 저장→새로고침→불러오기 성공 |
| 4. 부분 UI 연동 | 구현된 메인 작품 목록, 캔버스 저장/복원만 연결 | 기존 디자인 유지, 실제 저장 성공 |
| 5. Auth·권한 | UID 프로필, 닉네임 중복 허용, Firestore/Storage Rules | 동일 닉네임 가입 허용, 타 UID 접근 차단 |
| 6. 작품별 세션 | 세션 발급/조회/반납, 오프라인 기존 권한, 동일 탭 잠금 | 같은 작품 동시 편집 거부, 다른 작품 허용 |
| 7. Storage·Functions 동기화 | 불변 파일 업로드, 세션·버전 확정, 멱등 요청 | 업로드 실패/중복/버전 불일치에서 서버 작품 보호 |
| 8. 수정 이력 A 방식 | 텍스트 목록, 버전·레이어·시각 저장, 이어 그리기 승인 | 확정된 목록만 보임, 승인 후 최신 버전 편집 |
| 9. 강제 복구·오프라인 | 세대 증가, 이전 세션 차단, 복구 초안 보존 | A 오프라인→B 복구→A 재접속 테스트 통과 |
| 10. AI·운영 준비 | AI 제안 승인, 마이그레이션·인덱스·백업·모바일 성능 | 원본 보존·보안·복구 시나리오 확인 |

**협업 규칙:** DB 코드는 독립적인 저장 서비스/리포지토리와 서버 함수로 작성하고, 프론트엔드 팀원이 유지하는 화면은 필요한 위치에만 최소한의 함수 호출을 연결한다. 구현된 기능과 예정 기능을 문서·테스트에서 구별한다. `database` 브랜치에서 변경 후 리뷰를 거쳐 병합한다.

# 15. 필수 테스트 시나리오

1. **닉네임:** 서로 다른 UID가 동일한 닉네임으로 회원가입·프로필 변경에 성공한다.
2. **소유권:** 다른 UID는 작품·레이어·파일·이력·세션에 접근하거나 수정할 수 없다.
3. **작품 잠금:** A가 `pic` 편집 중 B의 `pic` 편집 요청은 실패한다.
4. **작품 독립:** A가 `pic` 편집 중 B는 `cat`을 편집할 수 있다.
5. **오프라인 유지:** A가 온라인에서 `pic` 권한을 받은 뒤 오프라인이 되어도 B의 `pic` 편집 요청은 차단된다.
6. **오프라인 신규 제한:** 세션이 없는 기기는 오프라인에서 새로운 서버 편집권을 획득하지 못한다.
7. **재동기화:** A의 로컬 작업은 온라인 복귀 후 세션·세대·버전이 유효하면 서버에 순서대로 확정된다.
8. **명시적 반납:** A가 동기화만 완료하면 B는 계속 읽기 전용이며, A가 정상 종료해 반납한 뒤에만 B가 새 권한을 받을 수 있다.
9. **이력:** B는 최신 서버 수정 이력을 확인하고 최신 버전에서 이어서 편집할 수 있다. 오프라인 미확정 변경은 이력에 표시되지 않는다.
10. **중복 저장:** `requestId`를 재전송해도 작품 버전·수정 이력이 중복 생성되지 않는다.
11. **서버 버전 충돌:** `expectedServerVersion` 불일치 요청은 기존 작품을 덮어쓰지 못한다.
12. **강제 복구:** A 오프라인 중 B가 강제 복구하면 `generation`이 증가하고 A의 재접속 저장은 거부된다.
13. **복구 초안:** 세션 무효화 후 A의 접근 가능한 로컬 작업이 유지되고 내보내기가 가능하다.
14. **저장 내구성:** PNG·객체·레이어 상태가 새로고침, 탭 종료, 편집 후 1·3·5·10초 종료 테스트에서 일관되게 복원된다.
15. **삭제·복제:** 삭제 표식이 오래된 기기에 의해 번복되지 않고 복제본의 수정이 원본을 바꾸지 않는다.
16. **AI 승인:** 적용 전 원본과 거절 결과가 보존되고, 오래된 버전의 AI 제안이 자동으로 적용되지 않는다.
17. **보안·비용:** Storage 파일 크기/형식, 객체 JSON 구조, AI 호출 횟수 및 서버 인증을 검증한다.
18. **환경 분리:** 테스트는 Emulator에서 수행하고 실제 운영 Firebase로 테스트 데이터가 전송되지 않는다.

# 17. 최종 합의 및 변경 관리

**이번 개정본의 최종 원칙:**

1. **작품별 한 기기 편집**(정확히는 서버가 인증한 하나의 작품별 세션).
2. **온라인 신규 권한 발급, 기존 권한의 오프라인 편집 허용**.
3. **동기화와 편집 권한 반납은 별도 절차**.
4. **수정 이력 A 방식: 서버 확정 내용 목록만 표시**.
5. **강제 복구 때 과거 세션 저장 차단, 로컬 복구 초안 보호**.
6. **닉네임 중복 허용, UID 기준 인증·소유권 관리**.
7. **기존 React 화면 최소 변경, IndexedDB + Firestore + Storage + Functions의 책임 분리**.

> 이 문서는 **개발 기준 계획서**다. 함수명·폴더 경로·색인·보존기간·AI 입력 형식 등의 구현 세부 항목은 실제 `IntelligentCanvas` 코드 분석과 팀원 합의 후 버전 관리한다. 서버에서 충돌성 덮어쓰기를 막는 것과 모든 오프라인 로컬 데이터의 무조건적인 복구는 동일한 보장이 아니다.
