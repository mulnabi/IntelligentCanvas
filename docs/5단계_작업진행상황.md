# 5단계 Firebase 서버 기반과 동기화

## 5-A 진행 기록

- `database` 브랜치에 기존 1~4단계 미커밋 변경이 있는 상태에서 시작했다. IndexedDB는 `IntelligentCanvasLocal` v3이며 `artworks`, `canvasContents`, `layers`, `layerContents`를 갖는다.
- 기존 Auth 9099, Firestore 8080, UI 4000 실행을 확인했다. 새 Storage 9199와 Functions 5001만 별도로 검증해 기존 프로세스와 로컬 데이터를 보존한다.
- Firebase 설정, Storage Rules, Firestore 작품 읽기 규칙, Web SDK 연결 모듈, Functions의 인증 확인 함수를 추가했다.
- Functions SDK와 Admin SDK를 서버 폴더에 설치했다. Edge에서 4종 연결·호출·규칙 검사 13개를 통과했다. 기존 기능 회귀 검사를 실행하는 중이다.
- 재개할 때는 두 Emulator Hub의 상태를 확인하고 이미 실행 중인 서비스를 겹쳐 시작하지 않는다. 아래 최종 결과가 없으면 기존 회귀 검사와 완료 기록을 마무리한다.

Storage SDK에는 `gs://intelligentcanvas-stage5a-local.invalid`를 명시한다. 이는 Emulator에서만 매핑하는 이름이다. `.firebaserc`의 `stage5a-local` 대상과 `firebase.json`의 Storage 설정을 함께 사용해 해당 이름에 Rules를 로드한다. 브라우저 Storage 초기화는 `VITE_FIREBASE_STORAGE_BUCKET` 값에 의존하지 않는다. 운영 버킷을 생성하거나 운영 Storage를 사용하지 않았다. [Storage Emulator 연결 문서](https://firebase.google.com/docs/emulator-suite/connect_storage)

Callable `checkServerEnvironment({})`은 인증된 자신의 `uid`와 `profileExists`를 반환한다. 데이터 요청에 UID를 넣으면 `invalid-argument`, 로그인이 없으면 `unauthenticated`, 로컬 서버 환경이 맞지 않으면 `failed-precondition`, Emulator Firestore 읽기가 실패하면 `unavailable`을 반환한다. Admin SDK는 서버 폴더에서만 사용하며 Functions Emulator 플래그, 프로젝트 ID, Auth와 Firestore의 로컬 포트를 확인한 후 읽는다. [Callable 공식 문서](https://firebase.google.com/docs/functions/callable) · [Firestore Admin SDK Emulator 연결](https://firebase.google.com/docs/emulator-suite/connect_firestore)

## Firestore 계약

| 경로 | 데이터와 5-A 권한 |
|---|---|
| `users/{uid}` | 기존 프로필의 `uid, nickname, createdAt, updatedAt, schemaVersion` 및 자체 프로필 정책 유지. 닉네임 중복 허용 |
| `users/{uid}/artworks/{artworkId}` | `artworkId, ownerUid, title, titleNormalized, widthPx, heightPx, backgroundColor, state, createdAt, updatedAt, serverVersion, schemaVersion`. 경로의 UID와 문서의 `ownerUid`가 일치하는 로그인 사용자만 조회 |
| `.../artworks/{artworkId}/layers/{layerId}` | `name, sortOrder, opacity, visible, isTemporary, category, currentRevisionId, pngPath, formatVersion, updatedAt`. 상위 작품 소유자만 조회 |
| `.../artworks/{artworkId}/editSession/current` | 예정 필드 `sessionId, deviceId, generation, status, startedAt, lastSeenAt, updatedAt`. 원본 문서의 직접 읽기·쓰기 차단 |
| `.../artworks/{artworkId}/revisions/{revisionId}` | 예정 필드 `serverVersion, requestId, sessionId, deviceId, changeType, changedLayers, summary, createdAt`. 원본 문서의 직접 읽기·쓰기 차단 |
| `.../artworks/{artworkId}/saveReceipts/{requestId}` | 향후 요청 지문과 확정 결과 기록. 원본 문서의 직접 읽기·쓰기 차단 |

작품 목록 조회는 `users/{uid}/artworks`에서 `ownerUid == uid` 필터를 사용한다. 레이어 권한은 상위 작품 문서까지 확인한다. 작품·레이어를 포함해 표의 서버 문서들은 클라이언트가 생성·변경·삭제할 수 없다. 5-B의 조회 응답은 `status` 등 화면에 필요한 정보만 제공하고 다른 기기의 `sessionId`는 숨긴다.

계획서의 `ownerUid`, `widthPx`, `heightPx`, `startedAt`을 우선했다. 요청에서 예로 든 `uid`, `width`, `height`, `acquiredAt`에 해당한다. 향후 첫 업로드 때 로컬 작품의 UUID와 레이어 ID를 서버 문서 ID로 그대로 사용하고, 서버 소유자는 인증 컨텍스트의 UID로 지정한다. 서버 `serverVersion`은 서버 확정 시에만 증가한다. 로컬 수정 시각과 서버 확정 시각, Dexie DB 버전과 서버 문서 스키마 버전은 각각 따로 관리한다.

5-A는 서버 작품을 자동 생성하지 않는다. 권한 검사용 문서는 테스트 실행의 신규 UID 아래에서만 준비하고 검사 후 삭제한다. 기존 IndexedDB v3와 작품·레이어 원본은 그대로 보존했다. 5-C·5-D에서 `syncQueue`와 `recoveryDrafts`를 추가할 경우 UID·작품 ID로 구분해 별도 테이블로 확장한다.

## Storage 파일 계약

| 용도 | 경로와 상태 |
|---|---|
| 연결 검사 | `_emulatorChecks/{uid}/{uuid}.txt`. 전용 버킷의 소유자만 256바이트 이하의 `text/plain` 생성·단건 조회·삭제 가능. 덮어쓰기와 목록 조회 차단 |
| 미확정 업로드 | `users/{uid}/artworks/{artworkId}/staging/{requestId}/{layerId}/raster.png`. 5-C용으로 경로를 예약했으며 현재 클라이언트 접근 차단 |
| 확정 원본 | `users/{uid}/artworks/{artworkId}/layers/{layerId}/{contentRevisionId}/raster.png`. 5-C용으로 경로를 예약했으며 현재 클라이언트 접근 차단 |

요청의 `versions/{version}` 경로 대신 계획서의 `contentRevisionId`를 사용한다. 작품 버전이 증가해도 안 바뀐 레이어는 기존 파일 참조를 재사용할 수 있다. 향후 서버는 UID·경로·크기·콘텐츠 유형·실제 PNG 헤더를 검증하고, 새 경로에 파일을 한 번만 작성한다. 그 다음 Firestore 트랜잭션에서 현재 `sessionId`, `deviceId`, `generation`, `expectedServerVersion`, `requestId`를 검사하고 새 파일 참조와 서버 버전을 함께 확정한다. 파일 작업은 재실행될 수 있는 트랜잭션 밖에서 처리한다.

업로드만 완료된 파일이나 확정에 실패해 참조가 없는 파일은 앱에서 읽을 수 있는 확정본과 분리한다. 정리 작업은 진행 중인 저장과 경합하지 않도록 취소·만료 상태를 확정한 뒤 유예 기간을 거치고, 현재 확정 참조가 없는 객체의 해당 세대만 제거한다. 유예 기간·PNG 용량 기준·다운로드 제공 방식은 5-C에서 결정한다. 5-A는 모든 작품 파일 경로를 닫아 두었다.

## VS Code와 브라우저에서 확인

1. 처음 실행하는 환경이면 프로젝트 루트에서 `npm.cmd --prefix functions ci`를 실행한다.
2. Emulator가 모두 꺼져 있으면 `firebase.cmd emulators:start --only "auth,firestore,storage,functions" --project ai-drawing-a9177`을 실행한다. 이미 실행 중이면 Hub의 `http://127.0.0.1:4400/emulators`와 필요 시 `4401/emulators`를 확인한다. 이번 검증에서는 기존 실행을 유지해 두 Hub로 나눠 사용했다.
3. 별도 터미널에서 `npm.cmd run dev -- --host 127.0.0.1 --port 5173 --strictPort`를 실행하고 기존 개발 환경처럼 앱에 로그인한다. 기존 작업을 확인할 때는 원래 브라우저 주소와 포트를 사용한다.
4. 브라우저 개발자 도구 콘솔에서 아래 코드를 실행한다. 로그인 UID의 임시 텍스트 파일을 올리고 다시 읽은 뒤 지운다.

```js
const { runServerEmulatorSmokeTest } = await import('/src/dev/serverEmulatorSmokeTest.js')
await runServerEmulatorSmokeTest()
```

Functions·Storage가 `ok`이고 `testObjectRemoved`가 `true`인지 확인한다. 가입 때 프로필까지 생성했다면 `firestoreProfileExists`도 `true`다. 자동 검사는 Playwright를 사용할 수 있는 환경에서 `node scripts/test-server-emulators.mjs`를 실행한다. `PLAYWRIGHT_MODULE_PATH`에 기존 검사와 동일한 Playwright 모듈 경로를 지정해도 된다.

## 5-B 재개 지점

인증 UID와 서버의 작품 소유권을 확인한 뒤 작품마다 `editSession/current`를 트랜잭션으로 처리한다. 동일 UID의 두 기기가 같은 작품을 동시에 열 때 한 기기만 편집 권한을 받고, 별개 작품은 동시에 편집할 수 있는지부터 검증한다. `getArtworkSession`의 공개 필드, 세션을 반납하는 최종 동기화 조건, 통신이 끊겼을 때 세션을 유지하는 규칙을 먼저 확정한다. 획·레이어 로컬 저장은 4단계 경로를 계속 사용한다.

한 번에 4종을 시작하는 방식과 Node.js 22 사용 자체는 이번 실행에서 별도로 시험하지 않았다. 서버 설정은 Node.js 22를 선언했고, 현재 PC의 Node.js 24에서 Functions Emulator 호출을 검증했다. 5-B~5-D 기능은 이 결과에 포함하지 않는다. [Functions 런타임 문서](https://firebase.google.com/docs/functions/manage-functions#set_nodejs_version)

## 5-B 진행 기록

- `database`에서 API·소유권 트랜잭션, 탭 별 자격 증명, 등록 작품의 읽기 전용 제어와 저장 경로 검사를 연결했다. Dexie v3 스키마를 유지한다.
- 세션을 획득하면 최초에는 읽기 전용이며 깨끗한 세션을 반납할 수 있다. 수정 시작은 서버에 미동기화 가능성을 먼저 기록한다. 이후의 반납은 해당 기록을 해제할 5-C 확정 API가 필요하다.
- `editSession/current`의 필드는 `sessionId, deviceId, generation, status, acquiredAt, updatedAt, tokenHash, localChangesPending`이다. 발급 때 세대를 증가시키며 서버는 원본 토큰을 저장하지 않는다. 조회의 `available/occupied/held` 응답에는 자격 증명을 담지 않는다.
- 서버 등록은 자신의 Firestore 작품 문서를 서버에서 읽어 확인한다. 온라인에서 미등록임을 확인한 작품과 이 앱에서 새로 생성한 로컬 작품은 오프라인에서도 기존 편집을 유지한다. 최초 분류나 서버 권한을 확인하지 못하면 읽기 전용이다.
- 자격 증명은 탭의 `sessionStorage`로만 새로고침에 이어지고, Web Locks로 같은 브라우저의 동시 편집을 막는다. 이미 확인한 세션은 오프라인에서 로컬에 저장할 수 있다. 탭 종료 또는 자격 증명 유실로는 서버 세션이 해제되지 않는다.
- Edge 격리 컨텍스트에서 세션 검사 9/9, 5-A 13/13, 작품 목록 24/24, 레이어 33/33 통과. 빌드 성공, lint 오류 0개·기존 경고 2개. `node scripts/test-edit-sessions.mjs`로 세션 검사를 재실행할 수 있다.
- 5-C에서는 서버 등록과 로컬 분류 전환, 파일 동기화 및 서버가 최종 확정한 버전과 반납 조건을 연결한다. 이미 수정 시작한 세션은 실제 변경이 적더라도 5-B에서 반납하지 않는다. 자격 증명을 잃었을 때의 명시적 복구는 5-D 범위다.

### 저장 구조와 재시도

- `IntelligentCanvasLocal` **v4**는 기존 `artworks`, `canvasContents`, `layers`, `layerContents`를 유지한다. 새 `artworkSync`, `syncQueue`는 `[uid+artworkId]`를 기본키로 사용한다. 그림·메타데이터 변경과 로컬 버전 증가·대기열 기록이 함께 성공하거나 함께 취소된다.
- 작품별로 전송 중인 스냅샷 한 개를 유지한다. 이후 변경은 별도 로컬 버전으로 남고, 먼저 보낸 요청의 영수증을 확인한 뒤 다음 스냅샷을 만든다. 재시도와 새로고침은 같은 요청 ID를 사용한다. 서버는 현재 세션 증명, 세대, 예상 서버 버전, 업로드된 PNG와 요청 지문을 확인한다. 충돌은 자동 병합하지 않는다.
- Firestore는 `users/{uid}/artworks/{artworkId}`에 작품·현재 레이어 묶음과 `serverVersion`, 하위 `layers/{layerId}`에 이름·순서·표시·불투명도와 파일 참조를 둔다. `saveReceipts/{requestId}`는 준비 상태와 확정 영수증을 기록한다. 서버 등록 v0은 첫 확정 후에만 목록에서 보인다.
- Storage의 새 파일은 `users/{uid}/artworks/{artworkId}/staging/{requestId}/{layerId}/{attemptId}/raster.png`에 올리고, 검증 후 `layers/{layerId}/{contentRevisionId}/raster.png`에 새 확정 파일을 만든다. 앱의 직접 Storage 접근은 차단하고 인증된 Functions가 읽기·쓰기를 중계한다. 현재 레이어별 서버 한도는 8 MiB이며 브라우저에서 만든 비인터레이스 8비트 RGB/RGBA PNG를 지원한다. 범위를 벗어나면 로컬 저장본을 유지하고 오류를 표시한다.
- 실패한 요청의 미확정 파일은 남을 수 있다. 같은 요청의 준비 기록을 재사용하며, 실행 중인 요청이나 확정 참조가 있는 파일을 안전하게 구별해야 하므로 이 단계에서는 자동 삭제하지 않는다. 다음 단계의 정리는 취소·만료가 확인되고 유예 기간이 지난 미참조 파일만 대상으로 한다.
- **서버 저장 후 편집 종료**는 입력을 잠그고 로컬 저장을 마친 뒤 대기열, 최신 로컬 버전과 확정 영수증을 확인한다. 서버는 동일 세션의 마지막 영수증과 최신 서버 버전을 확인하고 반납한다. 5-B의 **변경 없이 세션 반납**도 유지한다.

4. A의 개발자 도구에서 **Network → Offline**을 선택한 뒤 선을 추가하거나 레이어를 바꾼다. **이 브라우저에 저장됨**과 **서버 동기화 대기 중**을 확인한다. 강제 복구 없이 A를 온라인으로 바꾸면 대기열이 동기화되고, 명시적으로 종료할 때까지 세션이 유지된다.
5. 강제 복구를 시험하려면 A의 연결을 끊은 상태에서 B의 **서버 작품 보기**로 작품을 연다. 읽기 전용 안내를 확인하고 테스트 작품에서만 **강제 복구 → 확인**을 누른다. **수정 시작**을 누른 뒤 다른 그림을 그리고 **서버 동기화 완료**를 기다린다.
6. A를 다시 온라인으로 바꾼다. **서버 동기화 중지**와 **이 브라우저의 복구 초안**을 확인한다. **초안 미리보기**로 A의 그림을 확인하고, 필요하면 **별도 로컬 작품으로 복제**한다. B의 **수정 이력**을 열어 확정된 변경을 확인한다.

### 적용 범위

- 강제 복구 버튼은 서버 확정본이 있는 작품에서 제공한다. 최초 서버 저장 전 작품은 기존 로컬 원본과 대기열로 이어서 작업한다.
- 네트워크가 끊긴 상태에서 동일 탭을 새로고침하려면 앱 자원과 로그인 상태를 브라우저에서 읽을 수 있어야 한다. v4에서 이어지는 기존 세션은 온라인에서 증명을 한 번 확인해야 v5의 오프라인 새로고침에 사용할 수 있다.
- 수동 staging 정리는 알려진 종료 영수증의 파일만 대상으로 한다. 확정 경로에 쓰인 뒤 Firestore 저장이 실패해 참조가 없는 파일과 영수증이 없는 파일은 보존한다. [Storage 객체 세대 조건](https://docs.cloud.google.com/storage/docs/request-preconditions)

### 2026-11-21 강제 복구 후 서버 확정본 조회 수정
