# 4단계 작업 진행 상황

## 시작 상태

- `database` 브랜치의 기존 미커밋 변경과 IndexedDB를 보존한다.
- 기존 저장소는 `IntelligentCanvasLocal` v2다. 그림판은 단일 PNG를 저장하고 레이어 패널은 별도 목록을 보여 준다.
- 작품별 레이어 메타데이터와 최신 원본 PNG를 v3에 추가한다. v2 원본은 보존하고 작품을 열 때 디코딩을 확인한 뒤 한 레이어로 이전한다.
- 이 기록이 마지막이라면 레이어 Repository를 그림판의 원본 버퍼·합성·자동 저장에 연결하고, 브라우저 검사와 빌드·lint를 진행한다.

## 구현 및 검증 중간 기록

- Dexie v3와 레이어 Repository를 연결했다. v2에서 연 작품은 기존 PNG를 디코딩한 뒤 레이어와 함께 이전하며, v2 원본과 작품 수정일을 유지한다.
- 패널의 레이어 선택·추가·삭제·표시·불투명도·순서를 합성 화면과 연결했다. 선택한 레이어의 별도 원본 버퍼에 펜·지우개를 적용한다.
- 기존 자동 저장과 이동·로그아웃 전 저장을 재사용한다. 변경한 레이어의 PNG와 필요한 설정만 IndexedDB 트랜잭션에 반영한다.
- 초기 브라우저 실행에서 기존 작품 목록 24개와 이전·단일 레이어 회귀 28개가 통과했다. 빌드 성공, lint 오류 0개와 기존 경고 2개를 확인했다.
- 두 레이어 검사를 따로 실행해 6개를 통과했다. 반투명 합성은 PNG 디코딩 전후 브라우저 색상 반올림 차이가 있어 전체 픽셀에서 알파 1, 알파를 반영한 채널 값 2 이내를 확인한다. 메타데이터 변경 전후 원본 PNG와 재열기·F5의 복원본은 해시 일치를 검사한다.
- 이 기록이 마지막이라면 확장한 Canvas 전체 검사 결과를 확인하고 브라우저 결과를 보관한다.

## 저장 구조와 편집 방식

| 테이블 | 키와 역할 |
|---|---|
| `artworks` | 기존 작품 메타데이터와 수정일 |
| `canvasContents` | v2 PNG 원본 보관 |
| `layers` | `[uid+artworkId+layerId]`로 설정 저장. `[uid+artworkId+sortOrder]`로 패널 순서 조회 |
| `layerContents` | `[uid+artworkId+layerId]`로 각 레이어의 원본 PNG Blob, 크기, 저장 시각, 레코드 버전 저장 |

v3는 새 테이블 두 개를 추가한다. 작품을 열 때 기존 레이어가 없다면 PNG 디코딩부터 확인하고 새 레이어와 콘텐츠를 한 트랜잭션으로 기록한다. v2 PNG는 ‘기존 그림’ 레이어 한 장에 들어가고, PNG가 없는 작품은 ‘레이어 1’로 시작한다. 이전은 같은 작품에 한 번만 적용되며 작품 수정일은 유지된다.

계획서의 레이어 정렬 색인을 적용했다. 패널 맨 위를 `sortOrder = 0`으로 정하고 화면은 아래에서 위로 합성한다. 표시 여부와 불투명도를 바꿔도 원본 픽셀은 유지된다. 선택 상태는 화면에서 관리하며, 다시 열 때 패널 맨 위를 선택한다.

계획서의 `contentRevisionId`는 버전별 스냅샷을 가리킨다. 이번에는 각 레이어의 최신 원본 한 장을 보관하므로 작품과 레이어의 복합키로 직접 조회한다. 저장 뒤 변경 이력을 보관하는 리비전은 후속 작업이다.

별도 원본 Canvas는 기존 PNG가 있거나 첫 펜 입력이 들어온 레이어에 할당한다. 원본 한 장은 기존 16,777,216픽셀 한도를 사용한다. 합성 화면과 원본의 상시 버퍼 합계는 67,108,864픽셀로 제한한다. RGBA 약 256 MiB에 해당하며 인코딩·디코딩의 임시 사본은 이 계산에 포함되지 않는다. 실제 기기에서 더 이른 메모리 오류가 나면 저장본을 유지하고 안내한다.

## 직접 확인하는 방법

1. Emulator가 꺼져 있다면 프로젝트 루트의 첫 터미널에서 `firebase.cmd emulators:start --only auth,firestore --project ai-drawing-a9177`을 실행한다.
2. 두 번째 터미널에서 `npm.cmd run dev -- --host 127.0.0.1 --port 5173 --strictPort`를 실행한다. 기존 작품을 확인할 때는 처음 저장한 브라우저·주소·포트와 계정을 그대로 사용한다.
3. 개발 주소에 로그인하고 작품을 연다. 기존 3단계 작품이라면 레이어 메뉴의 ‘기존 그림’에 이전 그림이 표시된다.
4. 새 작품을 열고 기본 레이어에 파란 선을 그린다. 레이어 패널에서 새 레이어를 추가하고 그 위에 빨간 선을 겹쳐 그린다.
5. 위 레이어의 빨간 선 일부를 지운다. 아래 파란 선이 드러나는지 확인한다. 같은 레이어를 숨겼다가 다시 표시하고, 불투명도를 바꿔 본 뒤 줄을 끌어 순서도 바꿔 본다.
6. ‘이 브라우저에 저장됨’이 표시되면 작품 목록으로 이동한다. 다시 연 뒤 F5를 눌러 그림과 표시 여부·불투명도·순서가 복원되는지 확인한다.

## 완료 기록

| 검사 | 결과 |
|---|---|
| Edge·IndexedDB·로컬 Emulator의 그림판 검사 | 33/33 통과 |
| 로그인·프로필·작품 목록 회귀 검사 | 24/24 통과 |
| `npm.cmd run build` | 성공. 큰 JavaScript 청크 경고 유지 |
| `npm.cmd run lint` | 오류 0개. `ToolPicker.jsx`와 `Color.jsx`의 기존 경고 2개 |

두 자동 검사 모두 격리된 브라우저 컨텍스트를 사용했고 실행마다 만든 Emulator 계정·프로필을 정리했다. 브라우저의 미처리 예외와 허용하지 않은 요청은 0건이었다. 결과는 [레이어 저장 검사](./test-results/stage4-layer-persistence.json)와 [작품 목록 회귀 검사](./test-results/stage4-artwork-metadata.json)에 보관했다.

정상 앱 이동과 로그아웃 전에는 완료되지 않은 저장을 기다린다. F5·창 닫기·강제 종료 전에는 저장 표시를 확인해야 한다. 이번 실행은 강제 전원 차단, 실제 메모리·디스크 고갈, 다른 브라우저와 실제 모바일 펜의 동작을 검증하지 않았다. IndexedDB 데이터는 브라우저별 로컬 저장이다. 서버 동기화와 동시 편집 제어는 후속 단계에서 다룬다.
